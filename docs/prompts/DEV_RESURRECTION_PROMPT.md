# Dev Resurrection — Стартовый промпт сессии планирования

**Тип сессии:** планирование (не реализация).
**Версия проекта:** v4.8.0+ (после мёрджа F6 — PR #11 и hotfix миграций — PR #12; main = `410452a`).
**Ветка:** не создавать. Сессия read-only по коду; результат — план-документ.
**Результат сессии:** `docs/plans/DEV_RESURRECTION_PLAN.md` + согласованный порядок действий и список follow-up'ов в backlog.

---

## Зачем эта сессия

Локальный (и серверный) dev-стенд проекта **сильно отстал** от текущего состояния `main`. Это вскрылось при попытке провести smoke-test F6 (Scheduled Digests) — выяснилось, что dev-БД на схеме pre-F4, не управляется alembic'ом, и устаревшие данные в ней не позволяют валидировать ни новые фичи, ни существующий поведение по реальным сценариям.

Без здорового dev-стенда:
- любая следующая фича сольётся в main без smoke-валидации;
- следующая миграция повторит риск, аналогичный hotfix-у `e5f6a7b8c9d0` из PR #12;
- `migrate-users` и другие data-миграции продолжают накапливать долг — чем дольше ждём, тем сложнее воспроизвести исходное состояние.

Эта сессия — **отдельная инженерная задача** уровня «infra hygiene», а не довесок к фиче. Цель — спроектировать минимально достаточный план, который:

1. Приводит локальный dev в синхрон с `main`.
2. Приводит серверный dev в синхрон с `main`.
3. Предотвращает повторение ситуации (CI guardrails + runbook).
4. Готовит почву для отложенного smoke-теста F6.

## Текущее состояние (что мы уже знаем)

### Локальный dev
- Postgres-контейнер `tg_parser_postgres` (pgvector/pgvector:pg17), volume `tg_parser_pgvector17_data`, аптайм 35+ часов.
- Схема **pre-F4**: нет таблиц `users`, `user_auth_mappings`, `digest_subscriptions`; нет колонки `sources.owner_id`.
- В `processed_documents` колонка `processed_at` имеет тип **VARCHAR** (ISO-строки `2026-04-01T15:13:20Z`). Текущий код ожидает TIMESTAMP.
- **Нет таблиц `alembic_version*`** — схема создавалась НЕ через alembic (видимо `Base.metadata.create_all()` или ручной SQL).
- Данные: 5 каналов в `sources` (`AgeManagment`, `Lab4health`, `LongevityClub`, `genotek`, `labdiagnostica_logical`), `processed_documents` ≈5400 строк суммарно. Самый свежий `processed_at` — **2026-04-01** (~18 дней назад).
- В `.env` есть всё необходимое: PG creds, MTProto creds (`TELEGRAM_API_ID/HASH/PHONE`), API-ключи OpenAI/Anthropic/Gemini, `BOT_ALLOWED_USERS=5303033376,5445781511`.

### Серверный dev
- Используется только владельцем проекта (нет других пользователей).
- Реальных пользовательских данных нет: только ingestion + topicization output для тех же каналов.
- Точное состояние схемы и версий — **проверить в начале сессии**.

### Состояние main (актуальное)
- F6 Scheduled Digests влит (`410452a`), миграция `f6a1b2c3d4e5` (digest_subscriptions, FK на users.id ON DELETE CASCADE).
- Hotfix дубликата alembic revision влит (`189db2a`) — линеаризованная история по всем 3 БД (ingestion / raw / processing).
- `tg-parser db history --db {ingestion,raw,processing}` показывает single head на каждую БД.

### Smoke F6 — отложен до починки dev
- Бот `@Tgingest_bot`, токен есть, chat_id `5445781511` (личка с ботом).
- Канал для smoke: `labdiagnostica_logical`.
- План smoke-теста (9 пунктов: happy path, empty tick, backlog cap, reconcile, stale-sub race, long digest, failure modes, ownership, cleanup) уже есть в transcript предыдущей сессии — не переписывать, использовать как есть после dev-resurrection.

## Цели планирования

К концу сессии у нас должен быть **один документ** — `docs/plans/DEV_RESURRECTION_PLAN.md` — со следующими разделами:

1. **Decision matrix: in-place vs full rebuild.** Сравнить два пути:
   - **In-place patch** — попытаться накатить F4 + F5 + F6 миграции на существующую pre-F4 БД с грязной схемой и устаревшими типами. `migrate-users` нужно валидировать на текущих данных.
   - **Full rebuild** — drop volume, накатить весь head с нуля, переимпортировать каналы, дождаться backfill 24-48 часов.
   - Аргументы за/против каждого, итоговая рекомендация и обоснование.

2. **Audit existing data.** Что в текущей dev-БД ценно сохранить (и нужно ли вообще)? Если решено rebuild — нужен ли `pg_dump` бэкап «на всякий случай»? Если in-place — какие данные пострадают на стыке VARCHAR→TIMESTAMP?

3. **Local execution plan.** Пошаговая инструкция для локального dev:
   - бэкап (если нужен);
   - подготовка `.env` (если нужны изменения, например `DIGEST_SCHEDULER_ENABLED`);
   - команды up/upgrade/migrate-users/add-channel в правильном порядке;
   - время на каждый шаг (особенно backfill);
   - критерии успеха каждого шага.

4. **Server execution plan.** Аналогично, но для серверного dev. Особенности:
   - downtime-окно (всё равно нет других пользователей, но процедурно);
   - доступы (ssh, sudo, docker permissions — кто и как);
   - отличия от локального процесса.

5. **Verification plan.** Что прогнать после resurrection чтобы убедиться, что dev «живой»:
   - базовый ingest нового сообщения в проингестированный канал;
   - topicization → проверить появление topic_cards;
   - search через `search_knowledge_base`;
   - bot Q&A через `ask_question`;
   - smoke F6 (передать в следующую сессию).

6. **Runbook.** Файл `docs/runbooks/DEV_RESURRECTION.md` — короткая процедура «как поднять dev с нуля», чтобы это можно было воспроизвести через 3 месяца без этого транскрипта. Должна включать: prerequisites, env vars, alembic команды, типичные грабли.

7. **CI guardrail.** Что добавить в `.github/workflows/ci.yml`, чтобы дубликат `e5f6a7b8c9d0` (как в PR #12) ловился при PR-time, а не на проде. Минимум:
   - проверка что `alembic heads --db {ingestion,raw,processing}` возвращает по одному head;
   - проверка что `alembic check` не находит несоответствий между моделями и миграциями;
   - идея: smoke-катание чистой `alembic upgrade head` + `alembic downgrade base` в Postgres-контейнере CI.

8. **Out-of-scope для этой работы.** Чтобы не разрастаться: список вещей, которые НЕ делаем в рамках dev-resurrection (например, миграция SQLite→Postgres, апгрейд Python, рефакторинг env-файла), с пометками куда перенести.

## Вопросы для обсуждения с пользователем

Сессия — диалог. Не приступать к написанию плана пока не получены ответы (или явное «решай сам») по этим пунктам:

### A. Серверный dev
1. Где физически находится серверный dev (домашний сервер, VPS, домен)? Какая ОС, версия Docker?
2. Какова **текущая** версия схемы там — такая же отсталая как локально, или ещё более старая/более новая? (Нужно ли проводить аналогичный audit перед планированием.)
3. На сервере какие **сторонние** сервисы крутятся вместе с tg_parser? Есть ли риск задеть их при пересоздании Postgres-контейнера / volume?
4. Есть ли SSH-доступ + права на `docker compose` / `tg-parser` CLI у того, кто будет выполнять resurrection?

### B. Стратегия — in-place или rebuild
5. Насколько ценны 5400 ingested processed_documents в локальном dev? (Подсказка: они на устаревшей схеме `processed_at VARCHAR` — даже если их перенести, для F6 cursor-mechanism они малопригодны).
6. Есть ли что-то, что было сгенерировано **в этой dev-БД** и нет в исходных Telegram-каналах (например, ручные правки тем, custom topic_cards, прокатанные эмбеддинги, которые жалко терять)? Если нет — full rebuild чистый и быстрый.
7. На сервере — то же самое, или там данные более ценные?

### C. Время и порядок
8. На какую длительность сессии планирования рассчитываем (45-60 мин планирование + потом отдельная исполнительная сессия 1.5-3 ч)?
9. Локальный и серверный dev — делаем последовательно (сначала локально → проверили → затем сервер) или параллельно? Я бы советовал последовательно, чтобы локально отработать процедуру и зафиксировать в runbook, прежде чем катить на сервере.
10. Канал `labdiagnostica_logical` — единственный для backfill, или подключать сразу 5 как сейчас? Чем меньше — тем быстрее resurrection и smoke-test, но меньше реальная нагрузка для проверки.

### D. Долгосрочные follow-up
11. После resurrection — добавляем в `docs/notes/FUTURE_FEATURES.md` пункт про необходимость **CI-job для alembic guardrails** как отдельную инфра-задачу, или включаем в этот же план?
12. Стоит ли в плане предусмотреть **второй runbook** — «как накатить новую миграцию на dev безопасно», чтобы избежать накопления нового долга в будущем?

## Out of scope для этой сессии

Ниже — то, что **намеренно не обсуждаем** в рамках dev-resurrection (если всплывёт — записываем в backlog как отдельные задачи):

- Дизайн новых фич (F7, и далее).

- Изменения схемы БД, не требуемые для приведения dev к head.
- Реальный smoke F6 — он откладывается на следующую сессию после resurrection.

## Инструкции для агента

1. **Не начинать реализацию.** Эта сессия — обсуждение и проектирование. Любые `git commit`, `docker compose up`, `alembic upgrade` и аналогичные мутирующие операции — **запрещены**, кроме read-only диагностики (`git log`, `tg-parser db history`, `docker ps`, `psql … -c "select …"`).
2. **Начать с раздела «Вопросы для обсуждения с пользователем» (A→D)**. Не переходить к написанию плана, пока ответы не получены или явно делегированы (`решай сам`).
3. **План создавать в файле** `docs/plans/DEV_RESURRECTION_PLAN.md` (создать новый), следуя структуре раздела «Цели планирования» выше.
4. **Не повторять smoke-test plan F6** — он уже зафиксирован в transcript предыдущей сессии. План резурекции должен только указать «после resurrection — провести smoke F6 по плану из transcript X», без дублирования содержания.
5. **Если в процессе обсуждения вскрывается ещё один блокер** (типа дубликата revision из PR #12) — фиксировать его в отдельном разделе плана «Известные блокеры», но не пытаться решить в рамках этой сессии.
6. **Tone:** прагматичный, без избыточной церемонии. Предлагать конкретные решения, обозначать trade-off'ы, рекомендовать default'ы.
