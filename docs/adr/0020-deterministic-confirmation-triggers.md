# ADR 0020 – Детерминированные триггеры подтверждения: закрытый пользовательский словарь вместо вывода намерения из прозы LLM

## Статус

**Accepted (2026-07-31).** BUG-086 follow-up, [issue #359](https://github.com/AlexEfimov/TG_parser/issues/359).

намеренно: это первое нормативное утверждение о **протоколе подтверждения**
bot-адаптера, и без него ничто, кроме нарратива в `BUG_LOG.md`, не удерживает

(PR [#358](https://github.com/AlexEfimov/TG_parser/pull/358)) был ADR-free, потому
что чинил один инструмент; **правило** ниже действует на все **16** tool'ов
`_WRITE_TOOLS_REQUIRING_CONFIRM` и на каждый будущий.

## Контекст

Framework вооружает `ConfirmFlow` **только** из `{"preview": True}`, возвращённого
executor'ом (BUG-002 / BUG-009 / BUG-046). Report-only форма внутри confirm-gated
write-tool'а (`dry_run` у `force_resummarize`) создаёт **preview-less turn**:
инструмент вызван, preview не получен, вооружать нечего. LLM в такой ситуации
дописывает собственное «Подтвердите … [да/нет]», после чего пользовательское «да»
не имеет адресата — исходный dead-end BUG-086.

Первая попытка ремонта (слой (c), `_recover_llm_authored_confirm`) **предсказывала
просьбу подтвердить по итоговому тексту turn'а** регулярным выражением. Результат:

- **шесть FP-векторов за четыре раунда ревью**, из четырёх исправленных **три
  морфологические** — лицо («подтверждаю»), финитность (деепричастие
  «подтверждая»), наклонение (инфинитив «подтвердить»); лексическим был только
  первый (голое `confirm`);
- два оставшихся вектора **структурно недостижимы** регуляркой: (a)
  disclaimer-вето чувствительно к порядку слов, а в русском он свободный; (b)
  детектор читает финальный текст turn'а, куда попадает **чужой текст, переданный
  инструментами** (процитированный пост или заголовок темы с «Подтвердите …
  [да/нет]»), поэтому preview может быть вооружён по тексту, который никто не
  писал как просьбу.

Попытка измерить частоту FP в проде (shadow-слой (d), поле `read_only_intent`)
**не дала и не может дать данных** по двум независимым причинам: вердикт
вычислялся *после* detector-гейта, т.е. писался только когда guard уже сработал;
и conversational-трафика на single-user-деплое нет вовсе (проверено 2026-07-31 —
за пять суток после деплоя все записи `agent_tool_call` относятся к owner-e2e
26 июля). ⇒ решение принимается **на design-основаниях**; секция issue
«Prioritise with data» считается исполненной, знаменатель равен нулю и это
потолок, а не warm-up.

Дефект — не в конкретной регулярке, а в **подходе**: framework выводил control
flow из открытой, порождаемой LLM прозы.

## Решение

### 1. Framework никогда не выводит control flow из прозы, сгенерированной LLM

Нормативно. Текст, который LLM вернула в turn'е, — **контент для пользователя**, а
не сигнал управления. Ни арминг FSM, ни выбор ветки, ни восстановление после
ошибки не имеют права зависеть от разбора этого текста. Это относится и к тексту,
пришедшему из инструментов и процитированному в ответе (вектор (b) выше).

### 2. Детерминированные триггеры берутся из закрытого словаря, который печатает пользователь

Источник — `classify_confirmation_token` ([`handlers.py`](../../tg_parser/bot/handlers.py),
ужесточён после BUG-032): `AFFIRMATIVE_TOKENS` (18) и `NEGATIVE_TOKENS` (14).
Словарь **закрыт и версионируется в коде**, в отличие от безграничной прозы.

⚠️ **Нормативное уточнение (round-2 review; уточнено после ревью реализации).** Для
*возобновления write-intent'а* засчитывается **вся нормализованная форма целиком** —
с точностью до **хвостовой** пунктуации (`,.;:!?`), которая снимается: «да.» — тот же
голый ответ, что и «да», а ни один токен обоих словарей пунктуации не содержит.
Tier-2 (первый токен составного ответа, строки 488–492) применять **нельзя**: он
классифицирует «да, покажи темы канала X» как affirmative, из-за чего после честного
dry-run отчёта был бы вооружён мутационный preview, а сам запрос пользователя молча
потерян. Составные ответы = `unrelated` ⇒ падают в агента; снятие хвостовой пунктуации
этого не ослабляет — опасен в компаунде **текст после разделителя**, а он strip'у не
поддаётся и по-прежнему не проходит словарь. Для существующего `ConfirmFlow` поведение
tier-2 сохраняется без изменений.

### 3. Восстановление после preview-less write-вызова — persisted snapshot + строго смежное подтверждение

Turn, вызвавший confirm-gated write-tool без preview, сохраняет snapshot
`{tool_name, args}` в FSM; `confirm` и все ключи `_PREVIEW_SUPPRESSING_ARGS`
вырезаются **в момент записи**, поэтому мутационную форму нельзя восстановить из
storage даже случайно. Snapshot **снимается в начале `handle_text`** и передаётся
роутеру параметром — иначе любой ранее возвращающий FSM-гейт оставляет его жить,
и «да» через два turn'а вооружает мутационный preview (round-2 BLOCKER).
Прецедент формы — persisted intent-роутеры **BUG-048 Part A** (`delete_intent`) и
**BUG-050** (`subscribe_intent`); BUG-047 — pre-router, разрешающий цель в том же
turn'е, и прецедентом здесь **не является**.

TTL — `PENDING_TTL_SECONDS`, направление отказа **fail-closed**: нераспарсенный
или отсутствующий таймстемп считается протухшим (существующий
`_is_pending_expired` fail-open и для этого пути непригоден).

### 4. Report-only флаг на confirm-gated write-tool'е обязан быть зарегистрирован

Любой `dry_run` / `simulate` / `report_only`-подобный аргумент у инструмента из
`_WRITE_TOOLS_REQUIRING_CONFIRM` регистрируется в `_PREVIEW_SUPPRESSING_ARGS`.
Реестр — нормативный, нарушение ловится tripwire-тестом в CI
(`TestPreviewSuppressingArgRegistryIsComplete`), а не ревью.

## Отношение к другим ADR

- **ADR-0004 (hexagonal / module boundaries)**, **ADR-0006 (§ «bot изолирован как
  адаптер»)** — правило целиком внутри bot-адаптера; домен и сервисы не знают о
  протоколе подтверждения и не меняются.
- **ADR-0017 (dependency policy)** — новых зависимостей нет; `pyproject` /
  `requirements` не трогаются.
- ADR, описывающего bot-FSM или confirm-протокол, до сих пор **не существовало** —
  этот первый.

## Последствия

- **Деградированный путь стоит двух подтверждений.** Если LLM выбрала неверную
  форму вызова, «да» показывает настоящий preview, второе «да» коммитит. Happy
  path (`confirm=false`) остаётся с одним подтверждением. Форма уже отгружена в
  BUG-047 `delete_suggest` clarify.
- **Худший исход ложного триггера смещается и обесценивается.** Раньше ложное
  срабатывание давало *вооружённый мутационный preview*, где случайное «да» уже
  коммитило. Теперь ложный триггер невозможен без явного действия пользователя, а
  его цена — **один preview: 0 токенов, 0 записей**, который всё равно нужно
  подтвердить против явного мутационного текста.
- **Морфологический класс дефектов исчезает вместе с подходом.** Удаляются
  `_LLM_AUTHORED_CONFIRM_PATTERN`, `_CONFIRMATION_DISCLAIMED_PATTERN`,
  `_ARG_LITERAL_PATTERN`, все пять precision-проходов и весь shadow-слой (d).
- **Affirmative-токен получает третье значение на уровне handler'а** (ConfirmFlow,
  delete/subscribe-роутеры, write-intent). Взаимное исключение обязано быть
  **доказуемым**, а не подразумеваемым: два механизма подтверждения не могут быть
  вооружены одновременно.
- **Корпус из пяти precision-проходов не выбрасывается**, а переиспользуется как
  инвариант-тест «финальный текст turn'а никогда не вооружает `ConfirmFlow`» —
  исполняемое доказательство независимости от прозы.
- **Enforcement — тест плюс этот ADR.** Автоматического валидатора ADR в проекте
  нет: механическую защиту даёт CI-тест, а ADR даёт ему обоснование, без которого
  тест однажды удалят как устаревший.
- **Deploy — bot-adapter only:** re-create `tg_bot` (BUG-078: re-create, НЕ
  `restart`), без миграций и без backup-требования.
