# Runbook — BUG-097 (a): дедупликация перестаёт считаться отказом (деплой + watch)

**Создан:** 2026-08-13 (сессия R10). **Статус: ВЫПОЛНЕНО 2026-08-13** по GO владельца — merge `581edd1`, все шесть проверок §4 пройдены на первом же тике после деплоя. Фактические результаты вписаны в §4; дефект самой процедуры, найденный при исполнении (пересоздание контейнера сдвигает фазу тика, и ждать надо не «следующего часа», а «старта плюс интервал»), описан в §3 — читайте его, а не память о прошлом деплое.

**Что деплоим:** собственный исход для документов, отброшенных **post-LLM** дедупом ([BUG-097](../notes/BUG_LOG.md), половина **a**). Документ, который прошёл обработку и был отбракован как дубликат, раньше попадал в `failed_count` по остаточному принципу (`total − processed − skipped`) — и восемь совершенно здоровых источников сидели в постоянном ложном `degraded` с четырёхзначным `fail_count` и `last_error` вида «processed 0 of N attempted». Теперь у дубликата есть `deduplicated_count`, исключённый из `failed_count`, и `fail_count` / `last_error` / `degraded` описывают **только** отказы.

**Не docs-only:** меняется код processing-пайплайна и планировщика. Миграции **нет**, схема не тронута, `.env` не тронут. Половина **(b)** — порядок проверки относительно LLM-вызова — этим деплоем **не** закрывается и остаётся за R11.

## 1. Деплой

Процедура — [`PRODUCTION_DEPLOYMENT.md`](../../PRODUCTION_DEPLOYMENT.md). Пересоздавать контейнер, **не** `restart` (BUG-078); `up -d` без изменения rendered spec не пересоздаёт, поэтому `--force-recreate` обязателен (BUG-090).

```bash
ssh prod 'cd /home/user/TG_parser && git pull --ff-only'
ssh prod 'cd /home/user/TG_parser && docker compose build tg_parser'
ssh prod 'cd /home/user/TG_parser && docker compose up -d --no-deps --force-recreate tg_parser'
```

**Пересоздаётся ровно один контейнер, и это осознанно.** Планировщик и весь processing-путь живут в `tg_parser` — он и есть носитель фикса. `tg_parser_mcp` **не** трогаем: в MCP-пути не изменилось ничего, а пересоздание стёрло бы окно логов, на которое опирается сессия R1. `tg_bot` тоже не трогаем — правка его не касается; после `docker tag` его контейнер остаётся на прежнем образе, и в `docker ps` он показывается уже не тегом `tg_parser:latest`, а id `94b713377d91`. Это не расхождение, а нормальное следствие того, что тег переехал на новый образ, а контейнер — нет.

Фактически: prod HEAD `4da7025` → **`581edd1`** (совпал с `origin/main`), новый образ `a31981939e26`, контейнер пересоздан **18:27:05 UTC**, `healthy` через ~50 секунд, `GET /health` → 200.

## 2. Настройки и миграции — ничего

Ни migration, ни `.env`. Проверять `docker compose run --rm --no-deps tg_parser db upgrade` не нужно и не следует: схема не менялась, а лишний прогон на живой базе — это риск без цели. Ловушка allow-list'а `tg_parser` (BUG-092) здесь тоже не при чём: новых ключей конфигурации фикс не вводит.

## 3. Когда ждать проверки — и почему «следующий час» неверный ответ

⚠️ **Дефект процедуры, найденный при исполнении.** Естественная формулировка «дождаться следующего тика, они идут примерно раз в 30–40 минут» неверна дважды. Во-первых, интервал — ровно **3600 с** (`Added task incremental_pipeline with interval 3600s`). Во-вторых, и это важнее: `incremental_pipeline` — **interval**-задача APScheduler, а не cron, поэтому её фаза привязана к моменту старта процесса. До деплоя тики шли в :00–:01 каждого часа, потому что предыдущий контейнер поднялся около 14:00 UTC. Контейнер, пересозданный в 18:27:05, дал первый тик в **19:27**, а не в 19:00.

Практический вывод: после пересоздания первого тика надо ждать **до часа** от момента старта, и опорная точка — `Scheduler started` в логах, а не сетка часов в `last_success_at`. Проверять поллингом, а не «примерно тогда»:

```bash
ssh prod 'docker logs tg_parser 2>&1 | grep "Background scheduler started"'   # момент старта = начало отсчёта
ssh prod 'date -u -Iseconds'
```

Первый тик после деплоя: **19:27:27 → 19:28:45 UTC**, все 14 источников.

| 6 | Сверка с уже существовавшей метрикой | `ssh prod "docker exec tg_parser_prometheus wget -qO- 'http://localhost:9090/api/v1/query?query=tg_dedup_duplicates_detected_total'"` | значения совпадают с §4.2 и §4.3 канал в канал | ✅ AgeManagment 4, Docma_ru 8, Lab4health 5, foodf4thought 1, genotek 2, labdiagnostica_logical 3, mediamedics 2, tgnikitin 2 — **побайтово те же числа**, что в логах и в `source_attempts`. **Отдельно — агрегат, который и был симптомом.** За 41 час до фикса: 320 попыток с `success=false` (1108 документов, 1 495 164 токена) против 240 успешных (10 документов). После деплоя, за первый тик: **28 попыток, все `success=true`**, ни одной с `success=false`; 28 документов, 38 099 токенов. Восстановилось именно то, чего не хватало, — соответствие между «попытка помечена отказом» и «что-то действительно упало».

⚠️ **Наблюдение, не дефект:** на тиках, где обрабатывать нечего (`total_count: 0`), ключа `deduplicated_count` в `pipeline_stats` **нет** вовсе — такой тик возвращает короткий словарь по early-return. Читателю `details_json` полагаться на присутствие ключа нельзя, `.get(..., 0)` обязателен. Это поведение не новое (так же ведут себя `attempted_count` и `cooldown_skipped_count`) и фиксом не введено, но при чтении таблицы глазами выглядит как пропажа.

⚠️ **Метрика после пересоздания начинается с нуля, и мгновенный запрос сразу после деплоя пуст.** `tg_dedup_duplicates_detected_total` — процессный счётчик с метками по каналам, и до первого инкремента в новом процессе серий нет: `/metrics` отдаёт только `# HELP` / `# TYPE`, а instant-запрос к Prometheus — пустой вектор. Это ожидаемо и не признак поломки; база для сравнения берётся из истории Prometheus, а не из живого запроса:

```bash
ssh prod "docker exec tg_parser_prometheus wget -qO- 'http://localhost:9090/api/v1/query?query=tg_dedup_duplicates_detected_total&time=2026-08-13T18:20:00Z'"
```

## 5. Что этот деплой НЕ закрывает

Половина **(b)** BUG-097 остаётся `open` за сессией **R11**, и деплой ничего в ней не изменил: дубликат по-прежнему оплачивается LLM-вызовом, и оплачивается **каждым тиком**, потому что отброшенный документ не сохраняется и следующий `NOT EXISTS` снова видит его необработанным. Числа §4.2 — прямое тому подтверждение: те же 27 документов, 38 099 токенов за один тик, `processed_count: 0`. Фикс (a) сделал этот расход **видимым** (`deduplicated_count`, `source_tick_deduplicated`) вместо того, чтобы маскировать его ложным отказом; останавливать его — работа R11, первым шагом которой стоит запись факта отбраковки, а не перенос проверки.

## 6. Откат

Фикс аддитивен: новый счётчик, новый ключ в статистике, новая INFO-строка. Данных он не меняет — ни одной записи не создаёт и не переписывает, кроме `fail_count` / `last_error`, которые обнуляет штатная ветка `record_attempt(success=True)`. Поэтому откат безопасен и сводится к образу:

```bash
ssh prod 'docker tag tg_parser:pre-pr416-2026-08-13 tg_parser:latest \
  && cd /home/user/TG_parser && docker compose up -d --no-deps --force-recreate tg_parser'
```

Цена отката — возврат ложного `degraded`: следующий же тик снова запишет дубликаты в `failed`, и `fail_count` начнёт расти с нуля. Исторические значения до 1080 не восстановятся, и восстанавливать их незачем — они не описывали ни одного настоящего отказа.
