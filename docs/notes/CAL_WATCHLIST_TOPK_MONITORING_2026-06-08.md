# Watchlist `topk` rollout — план пост-деплой мониторинга (2026-06-08)

**Связано с:** ADR `docs/adr/0010-watchlist-keyword-aggregation.md`
**Деплой:** прод на `de0878b`, образ `tg_parser:latest`, конфиг live: `watchlist_keyword_aggregation=topk`, `watchlist_keyword_topk=3`, веса `0.4 / 0.6`.
**Статус:** наблюдение go-forward матчей под новой агрегацией. Документ операционный, не код.

---

## 1. Зачем наблюдаем

`topk` (capped recall, K=3) снимает «штраф знаменателя»: для on-topic документа достаточно попадания ≥3 ключей, чтобы `keyword=1.0`. Это поднимает recall у многоключевых паков (n≥4). Риск — обратная сторона: на широких каналах низкий порог может начать пропускать generic-посты. Цель мониторинга — поймать это раньше, чем пользователь увидит шум, и решить точечно (порог per-interest), не откатывая системный фикс.

Важно: `topk` — строгий no-op для интересов с ≤3 ключами (математически тождественно старому `mean`). Их можно из наблюдения исключить — их поведение не изменилось.

## 3. На что смотреть

1. **False positives на широких лаб-каналах.** Гл. подозреваемые: `kdl_ru`, `genotek`, `Lab4health` — generic «сдайте анализ на …». Признак: combined у порога (0.50–0.55), `keyword=1.0` при `semantic` низком (≤0.55), сниппет рекламный/нетематический.
2. **Объёмный флуд** у GLP-1 и Биомаркеров — не столько ложность, сколько частота нотификаций. Если матчей > ~3–5 в день и часть пограничная — кандидат на `+0.05`.
3. **Topic-bleed** (особенно mTOR/геропротекторы): доки на смежные темы (старение вообще), цепляющиеся 3 общими ключами. Проверять, что топ остаётся профильным.

Не-цели: интересы с ≤3 ключами; семантическая полнота (это не задача S1).

---

## 4. Критерий для `+0.05` к порогу (операционный, per-interest)

Поднять порог конкретного интереса на `+0.05` (напр. 0.50 → 0.55), если **за окно наблюдения (первые 7–14 дней потока)** выполняется любое из:

- доля off-topic среди новых матчей **≥ 20%** (ручная оценка ~20 свежих матчей), **или**
- ≥ 2 явных рекламных/generic false positives с `combined < порог+0.05` (т.е. их отсекает именно бамп), **при** отсутствии on-topic матчей в той же зоне `[порог, порог+0.05)` (т.е. бамп не режет полезное), **или**
- объём нотификаций субъективно «шумный» для владельца И верхняя зона `[порог, порог+0.05)` преимущественно off-topic.

НЕ поднимать порог, если в зоне `[порог, порог+0.05)` сидят on-topic доки (бамп срежет recall — а это ровно то, что мы чинили). В таком случае точечнее — `exclude_keywords` на мусорные триггеры.

Порядок выбора инструмента при шуме: **(1) `exclude_keywords`** (хирургически, без потери recall) → **(2) `+0.05` к порогу** (если шум диффузный) → **(3) сужение каналов** (только если конкретный канал — чистый источник мусора).

## 5. Как инспектировать матчи

- MCP: `get_watchlist_matches(interest_id, since_iso=...)` — сохранённые матчи со скорами; `list_watchlists` — обзор.
- Прод dry-run (read-only, без потока): `ssh prod 'cd ~/TG_parser && docker compose exec -T tg_parser tg-parser watchlist backfill <id> --since <ISO>'` (помнить про cap 2000 newest; для полного среза — in-container декомпозиция).
- Глазами проверять `keyword_hits/keyword_total` (теперь в `WatchScore`): низкий `hits` при высоком combined = матч держится на семантике → кандидат в шум на пограничье.

---

## 6. Аварийный откат

Системный откат к старой агрегации — без релиза, env на проде:

```
watchlist_keyword_aggregation=mean
```

затем recreate сервисов. Использовать только при широкой регрессии (массовый шум сразу по нескольким интересам), а не для точечного шума одного интереса — для последнего достаточно §4.
