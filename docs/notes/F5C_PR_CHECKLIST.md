# F5-C — PR checklist (с пометками karpathy-like)

**Назначение:** вставить в описание Pull Request для F5-C (Evolving Topic Summaries). Набор критериев **совпадает по смыслу** с разделом «PR checklist» в [`START_PROMPT_SPRINT_F5C.md`](START_PROMPT_SPRINT_F5C.md) (тот же текст буллетов, плюс пометки **karpathy-like**). **Порядок строк здесь другой:** сгруппирован по рекомендованным **коммитам 1/2 и 2/2**; компактный список в **исходном** порядке остаётся в спринт-промпте.

**Имя файла миграции** в буллете — пример из спринт-промпта; фактическое имя ревизии берётся из `ls migrations/versions/processing/` и следующего свободного слота (см. Шаг 2 спринт-промпта; текущий head — `c9d8e7f6a5b4`).

**Порядок коммитов** соответствует рекомендации из того же промпта: **1/2** — schema + service + counter + тесты ядра; **2/2** — scheduler hook + MCP/CLI + остальные тесты + документация. Bot tools в MVP **не добавляются** (Decision #9 — F5-C backend-фича без UX-сигнала).

**Согласованность с продуктовым § Level C:** в [`FUTURE_FEATURES.md`](FUTURE_FEATURES.md) § Level C говорится «при накоплении N новых supporting items»; **MVP default по спринт-промпту — N = 5** (env `RESUMMARIZE_TRIGGER_N`, обоснование — Decision #1 в `START_PROMPT_SPRINT_F5C.md`). В реализации и доках явно указать дефолт **5** и возможность тюнинга через env.

**Связь с D.1:** F5-C наследует **per-batch checkpointing** контракт D.1 (counter инкрементируется per-batch в `_update_bundles_for_assignments`). Однако **не** использует D.1-контракт `failed_stage='resummarize'`: по Decision #13 F5-C — post-processing, не core pipeline, и его сбои НЕ должны портить `success`-метрику source-attempt. Mirror F11-style silent log: не-billing exception → `logger.exception` без `stage_errors`; `AnthropicBillingError` → `stage_errors` для срабатывания billing-pause D.1-механизма. Подробнее см. Decision #13 в [`START_PROMPT_SPRINT_F5C.md`](START_PROMPT_SPRINT_F5C.md) и оригинал D.1 в [`START_PROMPT_SPRINT_D1_TOPICIZATION_HARDENING.md`](START_PROMPT_SPRINT_D1_TOPICIZATION_HARDENING.md).

## Опционально (раздел Risks исходного промпта; не в минимальном PR checklist спринт-промпта)

- [ ] Метрика `tg_resummarize_total{status}` с лейблами (ok / locked / empty_scope / llm_error / no_bundle / no_card / cap) — фундамент для калибровки `RESUMMARIZE_TRIGGER_N` и выбора model в проде. **(karpathy-like: замкнутый цикл наблюдаемости — увидим, какая доля re-summarize реально полезна, а какая идёт в no-op skip'ы.)**
- [ ] Метрика `tg_resummarize_tokens_total{model, type}` — мониторинг TCO; алерт при `> 100K tokens / day / channel` (явно превышает разумный budget при `RESUMMARIZE_MAX_TOKENS_PER_TICK=50000` × ~24 ticks/day = 1.2M tokens upper bound). **(karpathy-like: явный финансовый контракт с пользователем за autonomous LLM operations.)**
- [ ] Race condition при `version_no = MAX+1`: одна `IntegrityError` на UNIQUE → один retry с фрешим MAX (gotcha #2). Если retry тоже падает — log warning, status `llm_error`, метрика. **(karpathy-like: graceful retry, not silent corruption.)**
- [ ] LLM возвращает невалидный JSON: ловим `(JSONDecodeError, KeyError, TypeError)` → status `llm_error`, версия НЕ создаётся, карточка не меняется (gotcha #3). **(karpathy-like: bad LLM output не отравляет existing "страницу темы".)**
- [ ] При первом подключении нового канала с большим backfill — поток новых items может быстро поднять счётчик у >10 тем; `RESUMMARIZE_MAX_PER_TICK=10` обеспечит постепенный prog-ress (10 тем/tick × 24 tick/day = 240 тем/day обработано), без runaway. **(karpathy-like: controlled assimilation — bandwidth-limited evolution.)**
- [ ] В описании tool `get_topic_versions` (MCP) кратко предупредить, что версии = audit, изменения карточки в реальном времени видны через `get_topic_details` (поле `summary_version` показывает текущую). **(karpathy-like: честный контракт с агентом — audit ≠ live state.)**
- [ ] В описании tool `force_resummarize` (MCP, admin) предупредить о LLM cost (1 вызов = ~5-10K tokens на gpt-4o-mini, ~$0.001-0.002). **(karpathy-like: явная стоимость admin-операции.)**
