## 1. Почему эта сессия существует и почему она первая на MCP-поверхности

Пока резолв личности fail-open, вердикт **любой** другой проверки прав условен: можно сколько угодно аккуратно фильтровать по `allowed_channel_ids`, если при ошибке БД вызывающий уже стал администратором с `allowed=None`. Отсюда жёсткая зависимость `R1 → всё остальное на MCP-поверхности` в §4 плана — она единственная в очереди, помимо `R2 → R3`.

Дефект **третий на том же участке кода** после BUG-001 (подделка идентичности) и BUG-001b (пустой static-mapping). Первые два защищали идентичность от подмены; этот — про её **потерю**, случай, которого ни один из шести существующих тестов не описывает.

## 2. Что установлено (не переоткрывать)

1. **Замер снят 2026-08-13 11:19 UTC.** `mcp.auth.static_fallback_used` = **0** за окно 2026-08-12 18:08 → 2026-08-13 11:19 (17 ч 11 мин), `identity_missing` = 0, аутентифицированных tool-вызовов в окне — **2**. Второе независимое окно (08-12 13:11–18:55, 10 вызовов) — тоже ноль.
2. **Продлевать замер логами бессмысленно.** Окно **скользит**, а не растёт: за 22 часа жизни контейнера в логе осталось 17 (`json-file`, `max-size=10m` × `max-file=3`). «Подождать сутки» не работает в принципе, а любой деплой окно обнуляет. Отсюда §3.3.
3. **Замер не разрешает удалять legacy-ветку.** Аутентифицированная выборка суммарно ~12 вызовов. Но форма фикса от замера и не зависит: разделение «UUID не резолвился → отказ» / «не-UUID → legacy admin» корректно при любом исходе измерения. Роль замера — исключить неожиданность, а не выдать лицензию на удаление.
4. **Механизм прочитан из кода** ([`mcp_server.py`](../../tg_parser/mcp_server.py) `resolve_mcp_user`, ветки на строках ~479–547): `except Exception:` логирует на `debug` и **проваливается** в тот же `return await get_default_admin()`, что и легальный static-путь. Плюс `get_owned_channel_ids` вызывается **внутри** того же `try`, поэтому под деградацию попадает каждый вызов не-администратора при любой ошибке БД.
5. **Окно на удалении пользователя — 60 секунд.** `resolve_user_by_auth` кэширует `CurrentUser` на `_CACHE_TTL = 60` ([`auth/resolvers.py`](../../tg_parser/auth/resolvers.py)), поэтому после удаления пользователя токен ещё проходит верификацию, а `get_by_id` уже возвращает `None` → admin до минуты.

## 3. Scope — строго в этом порядке

### 3.1 Red/green первым, до правок

Четыре ветви, из которых в наборе есть только две. Тест должен **падать** на сегодняшнем коде там, где сегодня выдаётся admin:

| Ветвь | Сегодня | Должно быть |
|---|---|---|
| `client_id` — UUID, резолвится | `CurrentUser` пользователя | без изменений |
| `client_id` — UUID, `db_user is None` (удалён / выдуман) | **default admin** | `PermissionError` |
| `client_id` — UUID, `get_by_id` роняет исключение | **default admin** | `PermissionError` |
| `client_id` — не UUID (legacy static client_name) | default admin | без изменений |

Отдельная ветвь, которую легко забыть, потому что она глубже: **исключение в `get_owned_channel_ids`** для не-админа. Сегодня она тоже даёт admin — то есть не-админ при сбое БД получает **больше** прав, чем при успехе.

Существующие тесты трогать не нужно, их надо **дополнить**: [`tests/test_mcp_auth_integration.py`](../../tests/test_mcp_auth_integration.py) покрывает шесть кейсов (`test_valid_bearer_yields_real_client_id_in_tool`, `test_meta_client_id_attack_is_ignored`, `test_missing_bearer_returns_401`, `test_invalid_bearer_returns_401`, `test_dev_mode_tool_call_resolves_to_default_admin`, `test_production_mode_no_identity_fail_loud`) — и ни один не проверяет «идентичность есть, но не резолвится». Причина в записи BUG-099 названа: тесты писались против BUG-001, где проблемой была подделка идентичности, а не её потеря.

### 3.2 Разделить два случая, слитых в один выход

`PermissionError` — не новый механизм, а тот же, которым уже отвечает ветка `client_id is None` при `mcp_auth_enabled`. Различитель — «является ли `client_id` UUID»: для static-пути это `client_name` из `MCP_AUTH_TOKENS`, для DB-пути — UUID пользователя. Решение о том, как именно проверять форму (парсинг `uuid.UUID` против запроса в БД), записать в сессии: проверка формы не ходит в БД и поэтому работает и при сбое БД — что здесь и требуется.

**Инвариант, который нельзя потерять:** dev-режим (`mcp_auth_enabled=False`) продолжает отдавать default admin — иначе локальная разработка встанет.

### 3.3 Счётчик Prometheus — обязательный deliverable, а не «наблюдаемость потом»

Без него следующий раз повторится ровно эта ситуация: событие есть только в логе, лог скользит, представительной выборки не существует. Метрика должна отвечать на **оба** вопроса одним рядом: жив ли ещё static-путь и случается ли деградация. Разумная форма — один счётчик с label'ом по исходу резолва (`resolved` / `static_fallback` / `unresolved_uuid` / `db_error`), по конвенции `tg_`-префикса из [`api/metrics.py`](../../tg_parser/api/metrics.py). **Не** размечать по `client_id` — это неограниченная кардинальность на публичной поверхности.

Порядок внутри сессии обязателен: сначала фикс (§3.2), потом счётчик. Счётчик, приехавший раньше, показывает исход, которого через час не будет, — это ровно та ошибка, которую R8 обошла порядком «фикс → разбор → метрика».

### 3.4 Сузить `except` и поднять уровень

`except Exception` → транспортные / `SQLAlchemyError`; `logger.debug("resolve_mcp_user: DB lookup failed…")` → `warning`. Сегодня событие деградации не видно на INFO, то есть прод по умолчанию его не пишет.

### 3.5 Снять обязательность мёртвого токена

`create_mcp_server` при `mcp_auth_enabled=True` и пустом `mcp_auth_tokens` падает с `RuntimeError` (guard BUG-001b, [`mcp_server.py`](../../tg_parser/mcp_server.py) ~393–406). Смысл guard'а — «не падать в admin молча» — надо сохранить, но сегодня он **обязывает** прод носить живой bearer-токен с правами полного администратора, которым никто не пользуется, и именно он делит код-путь с деградацией. Разрешить DB-only режим: `MCP_AUTH_ENABLED=true` при пустом `MCP_AUTH_TOKENS`. Текст самого `RuntimeError` это наполовину признаёт («Either provide static tokens or rely solely on DB-resolved tokens»).

### 3.6 Решение по близнецу на HTTP — записать, а не молча пропустить

[`api/auth.py`](../../tg_parser/api/auth.py) `resolve_current_user`: валидный статический `api_key` без DB-маппинга → `get_default_admin()` (строки 56–63). Ожидание **пришпилено тестом** `tests/test_f4_auth_resolution.py::test_valid_key_not_mapped_falls_back_to_admin`, то есть близнец останется незамеченным именно потому, что тест его благословляет. **Не чинить «по докстрингу»:** шапка той же функции уже пишет «Key not mapped to a user in DB → 403», а код и тест по-прежнему отдают admin. Это drift документации, не доказательство, что близнец закрыт.

**Рекомендация плана — записать диспозицию, код не трогать:** HTTP-поверхность в scope ревью не входила, своей улики по ней нет, а менять поведение, закреплённое зелёным тестом, без улики — значит угадывать. Но решение должно быть **явным**: «чиним тем же PR» или «диспозиция зафиксирована, сессия такая-то». Молчание здесь и есть дефект.

### 3.7 Вне scope

- **Bot-арм** — `user = current_user or await get_default_admin()` в 34 из 35 исполнителей [`bot/tools.py`](../../tg_parser/bot/tools.py). 34 точки правки и смена контракта сигнатуры; сегодня защиту реально держит `UserResolutionMiddleware`, а `handlers.py` называет свой отказ работать при `current_user is None` «load-bearing, not defensive». Место этой правки — hardening после R2, когда тестовая дисциплина «вызов без личности» уже выстроена.
- **Удаление legacy static-пути.** Замер этого не разрешает (§2 п.3).
- **60-секундное окно кэша** (§2 п.5). Отдельное решение: сокращать TTL, инвалидировать при удалении пользователя или принять как есть. Записать диспозицию, не чинить здесь — иначе сессия расползается на кэш-инвалидацию.
- RBAC read-путей — это R2.

## 4. Acceptance criteria

1. Красные тесты из §3.1 зелёные; в наборе есть все четыре ветви резолва плюс ветвь исключения в `get_owned_channel_ids`.
2. Dev-режим (`mcp_auth_enabled=False`) по-прежнему отдаёт default admin — доказать тестом, а не утверждением.
3. Счётчик из §3.3 существует, растёт на нужном исходе и покрыт тестом «метрика считает то, что обещает».
4. `MCP_AUTH_ENABLED=true` с пустым `MCP_AUTH_TOKENS` поднимается (DB-only), а смысл BUG-001b не потерян: молчаливого admin-fallback по-прежнему нет.
5. `TEST_POSTGRES=1` прогон зелёный (ожидание — порядок 4.2k+ passed, точное число командой из `tests/README.md`). Default тоже.
6. Диспозиция по HTTP-близнецу (§3.6) и по 60-секундному окну (§3.7) записана явно — в BUG-099 либо в план.
7. BUG-099 обновлён: что сделано, что осталось и за какой сессией.
8. Прод-smoke **после деплоя и только по GO**: рабочий токен продолжает работать, выдуманный UUID получает отказ.
