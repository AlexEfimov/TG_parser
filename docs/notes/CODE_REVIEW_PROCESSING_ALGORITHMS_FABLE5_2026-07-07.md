# Code-Review: алгоритмы обработки информации из Telegram-каналов (tg_parser)

**Дата:** 2026-07-07 · **Ревьюер:** Fable 5 (read-only) · **Задание:** `docs/notes/START_PROMPT_FABLE5_CODE_REVIEW_PROCESSING_ALGORITHMS_2026-07-07.md`

---

## 1. Резюме для руководителя

1. **Главная потеря качества (и денег впустую): ре-суммаризация тем (F5-C) работает без текста документов.** В `resummarization_service.py:277–285` LLM получает только `source_ref` / `role` / `score` / `justification` элементов бандла — ни `text_clean`, ни `summary` документов не передаются. Промпт (`prompts/resummarize.yaml`) при этом требует «DO NOT invent claims that are not supported by the items» — на входе, где утверждений фактически нет. Каждый ре-суммарайз тратит токены, но не может обогащать сводку содержанием. Это дефект уровня «фича не выполняет своё назначение» (F-02, Critical).
2. **Главная потеря токенов: точный дедуп срабатывает ПОСЛЕ LLM-вызова.** Хэш считается по `text_clean` — результату LLM (`pipeline.py:767–772`), а не по сырому тексту. Каждый точный репост/форвард оплачивается полным processing-вызовом (~2–4K токенов), после чего документ выбрасывается `_filter_duplicates`. Для моно-тематического кластера из 10 каналов с зафиксированными 916 cross-channel keyword-overlap (ADR-0016) это регулярный сжигаемый бюджет (F-01, High).
3. **Главная потеря скорости: тик планировщика квадратичен и грузит весь корпус канала дважды.** `scheduler_service.py:496–500` пересобирает множество `{dd.source_ref for dd in docs_before}` внутри list-comprehension **на каждый элемент** `docs_after` — O(N²) по числу документов канала; сами `docs_before`/`docs_after` — два полных `list_by_channel` (строки 296, 378) с полным текстом всех документов, хотя нужны только `source_ref`. На канале в 10K+ документов это доминирует время тика (F-03, High).
4. **Спорный алгоритмический выбор: «эмбеддинг темы» = эмбеддинг документа первого якоря.** И межканальная линковка (`topic_linking_service.py:107`), и cross-chunk консолидация full-run (`topicization_service.py`, `_finalize_full_run`) представляют тему вектором её первого якорного сообщения, хотя в системе уже существует инфраструктура тематических эмбеддингов (`run_topic_embedding` в `embedding_service.py`). Похожесть тем измеряется похожестью двух отдельных постов (F-04, High по качеству линковки).
5. **Инфраструктура LLM-слоя в целом зрелая** (адаптивный token-bucket с синхронизацией по заголовкам Anthropic, streaming stall-guard, refund-семантика, cooldown-лестница для billing/parse-фейлов, resumable full-run с чекпоинтами и circuit-breaker). Но TTL-кэш ответов фактически мёртв для пайплайна: он подключён только в `generate()` (`instrumented.py:42–56`), тогда как все стадии пайплайна ходят через `generate_with_usage()`; вдобавок глобальный кэш не включает provider/model в ключ — потенциальная отдача ответа чужой модели (F-06/F-07, Medium).
6. **Общая оценка зрелости: высокая для проекта этого размера.** Идемпотентность, advisory-локи, провенанс и деградация без падения ядра (ADR-0006) реально соблюдаются в коде. Основные проблемы — не «сломанность», а неоптимальность: LLM-вызовы там, где хватит хэша; полные корпусные загрузки там, где хватит одного SQL-запроса; и один содержательный дефект (F-02), который стоит закрыть в первую очередь.

## 3. Детальный разбор по алгоритмам

### A1. LLM-извлечение структуры из сообщений

**Что делает и где.** Один LLM-вызов на сообщение: system-промпт (`prompts/processing.yaml`) + текст сообщения (для комментариев — плюс текст родительского поста), ответ — строгий JSON (`text_clean`, `summary`, `topics`, `entities`, `language`). Параллельный путь `_process_batch_parallel` (`pipeline.py:1144+`): semaphore `processing_concurrency=5`, per-tick лимит 300 сообщений (`processing_tick_batch_size`), инкрементальная персистенция чанками по 20 (`_persist_chunk`), cooldown-лестница по типам фейлов (billing 1800s / parse 3 попытки → 24h / прочее 3600s, `settings.py:235–284`). JSON-устойчивость: `extract_json_from_response` + `repair_json` (unescaped quotes, trailing commas) + корректирующий hint на ретраях.

**Оценка по осям.**
- *Скорость:* хорошая; лимитируется RPM Anthropic (token-bucket) и semaphore=5. Существенный минус — пред-LLM проверка `exists()` в цикле по одному запросу на сообщение (`pipeline.py:1200–1204`): O(N) round-trip'ов, притом что `list_unprocessed_by_channel` уже отфильтровал обработанные через `NOT EXISTS` (`raw_message_repo.py:192–207`) — проверка почти полностью избыточна.
- *Качество:* промпт зрелый (правила экранирования кавычек, сохранение URL, режим комментариев с контекстом родителя); temperature=0; media-only сообщения обрабатываются программно без LLM (`_describe_media`) — правильная экономия.
- *Токены/стоимость:* system-промпт кэшируется (`cache_control: ephemeral`, `anthropic_client.py:205–209`; `anthropic_prompt_caching_enabled=True` — «~90% на повторных префиксах»). Главная утечка — дубликаты проходят полный LLM-вызов (см. A2). Один вызов на сообщение — оправданный выбор (изоляция сбоев, простой парсинг), но для коротких сообщений (реплики, эмодзи-комментарии) фикс-оверхед вызова велик.
- *Взаимодействие:* корректное — фейлы пишутся в append-only `processing_failures`, billing-ошибка (`AnthropicBillingError`) поднимается до планировщика и ставит источник на паузу.
- *Корректность выбора:* per-message LLM-экстракция — стандартное и обоснованное решение. Ломается на flood-каналах (сотни коротких сообщений: 300/тик — дни на разбор бэклога при потоке > ~7K/сутки).

**Альтернативы:** (а) упаковка K коротких сообщений в один вызов — экономит per-call оверхед, но повышает риск JSON-развала и потери одного сообщения из-за соседнего (существующая repair-машинерия смягчает, но не убирает); (б) дешёвый провайдер (haiku/gemini-flash/ollama) для сообщений < 200 символов — runtime-переключение стейджей уже поддержано `LLMConfigManager`.

**Качество реализации:** высокое; замечания — избыточный `exists()`-цикл (F-09) и последовательный путь `process_batch(concurrency=1)` с теми же одиночными запросами.

### A2. Точный дедуп (SHA-256 content-hash)

**Что делает и где.** `normalize_for_hash` (`domain/hashing.py`): опциональный срез query-string URL, lowercase, схлопывание пробелов; SHA-256 от результата. Хэш присваивается **после** LLM по `text_clean` (`pipeline.py:767–772`), проверка `find_by_content_hash` в пределах канала — в `process_message` (`:473–479`) и `_filter_duplicates` (`:1051–1142`, внутрибатчевый + БД-дедуп с сохранением порядка).

**Оценка по осям.** *Качество* — корректно: hash по стабилизированному LLM-ом тексту устойчив к вариациям форматирования; идемпотентность и cross-chunk дедуп через БД соблюдены (`:1113–1119`). *Стоимость* — ключевой дефект: дубликат распознаётся только после оплаченного LLM-вызова (F-01). *Скорость* — `_filter_duplicates` делает `find_by_content_hash` по одному документу (N запросов на чанк из 20 — терпимо, но батчится тривиально). *Выбор алгоритма* — SHA-256 по нормализованному тексту обоснован; ломается на «почти дублях» (эмодзи/хэштег добавлен) — это осознанно вынесено в A3/ADR-0016.

**Альтернатива:** второй хэш по нормализованному **сырому** тексту (`RawTelegramMessage.text`), проверяемый до LLM. Точность ниже (сырой текст шумнее), но точные форварды/репосты — а это основной класс дублей в моно-тематическом кластере — ловятся бесплатно. Нормализация из `hashing.py` переиспользуется как есть.

### A3. Near-duplicate observe (Phase 0)

**Что делает и где.** `near_duplicate_service.py`: для каждого нового документа — cosine (pgvector `<=>`) против скользящего окна последних N=50 эмбеддингов своего канала (intra) и остальных активных источников (cross); порог 0.92; только метрики/логи, ничего не мутирует (ADR-0016 Phase 0).

**Оценка.** Полностью соответствует принципу «наблюдай прежде чем решать» (ADR-0006 §6). Сложность O(new_docs × 2 окна) с индексным KNN — дёшево. Риск: cross-окно = «все остальные источники» — при росте числа каналов окно last-N по всем сиблингам может пропускать дубли от «тихих» каналов (repost старше окна); для Phase 0 (измерение rate) допустимо. Замечаний по реализации нет.

### A4. Эмбеддинги и подготовка текста

**Что делает и где.** `_prepare_text` (`embedding_service.py:82–89`): `summary + topics + text_clean[:500]`. Батчи по 100 (`embedding_batch_size`), модель `text-embedding-3-small`. Инкрементальный путь `run_incremental_embedding(new_doc_refs)` — только новые. Есть `run_topic_embedding` для карточек тем.

**Оценка.** *Стоимость/скорость* — хорошо: батчинг, инкрементальность. *Качество* — обрезка `text_clean` до 500 символов ощутимо для лонгридов: семантический поиск и watchlist-семантика видят только начало документа плюс summary (F-10). Смягчено тем, что summary включён. *Выбор* — text-embedding-3-small адекватен по цене; известный минус для русскоязычного медицинского корпуса зафиксирован самим проектом (`settings.py:1163–1165`: «Russian medical text ceilings ~0.3 cosine») — это довод в пользу либо более сильной модели эмбеддингов, либо большего веса keyword-компоненты (уже сделано в A11).

### A5. Полная топикизация (LLM-кластеризация)

**Что делает и где.** `topicize_channel` / `_topicize_channel_chunked` (`processing/topicization.py`): корпус режется на батчи по 50 документов, каждый батч — LLM-вызов (`prompts/topicization.yaml`, max_tokens 8192) с параллелизмом `topicization_batch_concurrency=5`; resumable-чанки по `topicization_full_chunk_batches=20` батчей, атомарный коммит чанка (cards+bundles+checkpoint), токен-бюджет, no-progress circuit-breaker (`topicization_checkpoint.py`). Обработка truncation: `stop_reason == "max_tokens"` детектируется (BUG-071), батч делится (`_generate_topics_batch_after_truncation`, `:1340–1391`). Качество тем фильтруется программно: singleton score≥0.75 и len≥300, cluster ≥2 якоря score≥0.6 (`_build_topic_card`).

**Оценка по осям.**
- *Скорость:* O(docs/50) LLM-вызовов + merge; на 10K документов ≈ 200 вызовов + merge — часы. Resumable-механика делает это управляемым.
- *Токены:* входы уже усечены в промпте (truncation `text_clean`/`summary` в `topicization_prompts.py`). Минус: при truncation-сплите половины батча переотправляются целиком — повторный input-токен на уже «увиденные» документы (смягчено тем, что сплит редок).
- *Качество:* батч из 50 документов — LLM видит только локальное окно; глобальные темы, размазанные по корпусу, собираются лишь на merge-этапе, где метаданные и состав уже с потерями (см. A6). Это фундаментальное ограничение LLM-кластеризации батчами.
- *Взаимодействие:* образцовое — advisory-локи (`TOPICIZATION_LOCK_NS`), чекпоинты в synthetic-строках `processing_failures`, детерминированный порядок `planned_refs_from_documents`.
- *Корректность выбора:* спорна на больших корпусах. LLM-кластеризация даёт хорошие названия/скоупы, но плоха как «кластеризатор» (окно 50, недетерминированные границы). Альтернатива — эмбеддинг-кластеризация (HDBSCAN/agglomerative на pgvector-векторах, они уже есть) + LLM только для нейминга/скоупа каждого кластера: LLM-вызовов O(topics) вместо O(docs/50), глобальная связность кластеров, детерминизм. См. §6.

### A6. Merge тем между батчами

**Что делает и где.** `_merge_topics` (`topicization.py:1393–1548`): компактный JSON всех тем → LLM возвращает `{"groups": [[0,5,12],[3],...]}`; метаданные группы берутся из **первого** члена (`primary = all_batch_topics[valid_ids[0]]`, `:1521`), якоря объединяются с дедупом по ref.

**Оценка.**
- *Токены:* хорошая идея — LLM отдаёт только ID (минимальный output), max_tokens=16384 с ростом при truncation, корректирующий hint на ретраях.
- *Качество:* два дефекта. (1) Метаданные «первого члена» произвольны — title/summary/scope самой информативной темы группы могут быть потеряны; логичнее брать члена с максимумом якорей или объединять scope_in. (2) `valid_ids = [mid for mid in member_ids if 0 <= mid < len(...)]` (`:1517`): темы, чьи ID LLM не вернул ни в одной группе, молча исчезают из результата; строковые ID дают `TypeError` — он теперь перехватывается выше как «failed merge chunk» (BUG-077, `:1023–1030`), т.е. не крэш, но целый чанк откатывается из-за одного кривого ID вместо коэрции `int(mid)`.
- *Fallback:* при пустых группах/неудаче возвращаются все батч-темы без слияния (`:1508–1512`) — деградация в дубли тем, не в потерю данных. Приемлемо.

### A7. Инкрементальный assign (keyword) + discover (LLM)

**Что делает и где.** Phase 1: `assign_documents_to_topics` — сопоставление токенов документа с ключевыми словами/scope тем, скор нормируется на число ключевых слов темы; порог; без LLM. Phase 2: `discover_new_topics` — несматченные документы батчами ≤50 (`topicization_batch_size`) уходят в LLM (`prompts/incremental_discover.yaml`) с списком существующих тем и cross-channel контекстом; маркеры «discover-attempted» предотвращают повторное скармливание одного документа; re-escalation до full-run с cooldown 3600s; standing-реконсиляция покрытия ≤200 док/тик (BUG-075).

**Оценка.** Это правильная реализация принципа «cheap hot path» (ADR-0006 §3): LLM только для остатка после keyword-фильтра. *Качество:* нормировка keyword-скора на `len(topic_keywords)` воспроизводит «denominator penalty», которую проект уже диагностировал и починил в watchlist (ADR-0010, top-k агрегация) — темы с богатым набором ключевых слов систематически недобирают скор, документы уходят в дорогой LLM-discover чаще, чем нужно (F-12: качество и стоимость сразу). *Взаимодействие:* discover-промпт просит LLM не создавать дубли существующих тем — но защита только промптовая; программной пост-проверки similarity новой темы против существующих на этом пути нет (в отличие от A8).

### A8. Cross-chunk консолидация full-run

**Что делает и где.** `_finalize_full_run` (`topicization_service.py`): пары тем сравниваются комбинированной метрикой cosine+Jaccard, порог `topicization_full_merge_threshold=0.6`, слияние с сохранением провенанса.

**Оценка.** *Выбор метрики* разумен (лексика+семантика). Дефект тот же, что в A9: cosine считается по эмбеддингу **документа первого якоря**, а не темы (F-04). Тема-кластер из 40 сообщений представлена одним постом; консолидация двух тем зависит от того, насколько похожи их случайно-первые якоря. Инфраструктура тематических эмбеддингов уже существует (`run_topic_embedding`) — она здесь просто не используется.

### A9. Межканальная линковка тем

**Что делает и где.** `topic_linking_service.py` (`link_topics`): все пары тем всех пар каналов, Jaccard по ключевым словам + cosine по эмбеддингам, порог `cross_channel_link_threshold=0.3`, создание TopicLink.

```104:109:tg_parser/services/topic_linking_service.py
        card_embeddings: dict[str, list[float]] = {}
        for card in all_cards:
            if card.anchors:
                emb = await embedding_repo.get_by_source_ref(card.anchors[0].anchor_ref)
                if emb:
                    card_embeddings[card.id] = emb.embedding
```

**Оценка.** *Скорость:* O(C²·T²) сравнений + N+1 фетч эмбеддингов по одному (`:107` в цикле — уже есть батчевый `get_many_by_source_refs`). При ~1000 тем это ~500K пар — на текущем масштабе минуты, растёт квадратично. *Качество:* эмбеддинг первого якоря (F-04) + низкий порог 0.3 (реальный avg-sim линков 0.33 по ADR-0016 — то есть порог почти не режет). *Альтернатива при росте:* pgvector KNN (HNSW-индекс по topic-эмбеддингам) — для каждой темы top-K соседей из других каналов вместо all-pairs, O(T·log T).

### A10. Гибридный поиск / RRF

**Что делает и где.** `retrieval_service.search`: semantic (pgvector) и keyword (FTS `ts_rank_cd`) ветки параллельно, слияние `rrf_fuse(k=60)` (`_ranking.py`), overfetch ×2, квота тем в контексте (`rag_topic_quota=2`), сборка структурированного контекста ([T]/[M]-блоки), ответ через `generate` (temperature 0.2, max_tokens 2048).

**Оценка.** *Выбор:* RRF — правильный, безнормировочный способ слить несравнимые скоры (cosine vs ts_rank); k=60 — литературный стандарт. *Скорость:* обе ветки конкурентны, репозитории индексные; узкое место — `create_embedding_client()` + HTTP-клиент на каждый запрос (`:119–124`), для чатбота с потоком вопросов это лишние ~десятки мс и сокеты на запрос (F-11). *Качество:* контекст-лимиты и цитирование по ref продуманы; `fts_min_rank=0.0` — keyword-ветка не отсекает шумные совпадения, но RRF-ранжирование это смягчает. Существенных претензий нет — самая аккуратная часть системы.

### A11. Watchlist-скоринг

**Что делает и где.** `compute_watch_score` (`watchlist_service.py:528+`): `0.4·keyword + 0.6·semantic`; keyword — top-k агрегация K=3 (ADR-0010, закрывает denominator penalty); semantic — cosine интереса против эмбеддинга документа; exclude_keywords — жёсткий фильтр. `check_interests`: батчевый фетч документов и эмбеддингов (BUG-055), затем двойной цикл интерес×документ (`:1228–1246`).

**Оценка.** *Выбор:* гибрид с data-driven калибровкой (симуляция по 15 интересам в ADR-0010) — образцовый процесс. *Скорость:* `_build_doc_tokens(doc)` вызывается внутри `compute_watch_score` (`:554`) — т.е. документ заново токенизируется и лемматизируется (pymorphy3) **для каждого интереса** (F-08): O(I×D) лемматизаций вместо O(D). `lru_cache` на `normalize_token` смягчает (повторные токены дёшевы), но на длинных документах и десятках интересов это заметный CPU в тике. *Взаимодействие:* деградация без эмбеддинга (keyword-only), auto-деактивация интересов заблокировавших бота — соответствует ADR-0006 §7.

### A12. Ре-суммаризация тем (F5-C)

**Что делает и где.** `resummarization_service.py`: триггер по счётчику `new_items_since_last_summary >= 5` или возрасту; advisory-lock на тему; лимиты — 10 тем/тик, 60s, 50K токенов/тик; версионирование прежней сводки (append-only `topic_card_versions`); optimistic locking.

**Критический дефект (F-02).** Payload для LLM:

```277:285:tg_parser/services/resummarization_service.py
        items_payload = [
            {
                "source_ref": it.source_ref,
                "role": it.role.value,
                "score": it.score if it.score is not None else 0.0,
                "justification": it.justification or "",
            }
            for it in input_items
        ]
```

Ни `text_clean`, ни `summary` документов не передаются. `justification` для keyword-матчей — строка вида «keyword overlap: …», для якорей — пустая. Т.е. LLM просят «обновить сводку с учётом нового материала», не показывая материал: единственные содержательные входы — старый title/summary/scope и списки ref'ов со скором. На практике модель либо перефразирует старую сводку (безвредно, но вызов потрачен впустую — до 10 вызовов×4096 max_tokens на тик на канал), либо галлюцинирует «новые аспекты» из названий ключевых слов в justification. Промпт-инструкция «DO NOT invent claims that are not supported by the items» невыполнима.

*Прочее:* новый LLM-клиент создаётся на каждую тему внутри `resummarize_topic` — httpx-клиент и rate-limiter-обвязка на вызов (F-11); окно top-N (якоря-первыми) — правильный выбор при условии, что в payload появится текст.

### A13. Rate-limiting / retries / кэш LLM

**Что делает и где.** `rate_limiter.py`: async token-bucket по RPM/ITPM/OTPM с консервативным Tier-1 fallback (50 RPM), адаптация лимитов и остатков по заголовкам `anthropic-ratelimit-*`, `reconcile_usage` (возврат разницы оценка−факт), `refund_acquire` на неуспех, `suggested_parallel_cap` (≤60% остатка окна). `anthropic_client.py`: retry 429/5xx/520 с retry-after/exp-backoff, aggregate wall-clock timeout 420s, streaming-путь с inter-event stall-guard 30s и защитой от truncated stream (обязательный `message_delta`), refund на каждом фейле, `stop_reason` наружу, prompt-caching. `response_cache.py` + `instrumented.py`: глобальный TTL-кэш 5 мин / 500 записей.

**Оценка.** Лимитер и клиент — сильная, продуманная инженерия; учётная дисциплина (acquire→reconcile/refund ровно один раз на попытку) выдержана и задокументирована. Два дефекта в кэше:
1. **Кэш не работает для пайплайна.** Подключён только в `generate()` (`instrumented.py:42–56`); `generate_with_usage()` (`:66–96`) идёт мимо кэша — а именно им пользуются processing/topicization/discover/merge/resummarize. Фактическая зона действия кэша — только RAG-ответы через `generate`. Для пайплайна это скорее корректно (одинаковые промпты там редки), но означает, что «F8-A cache» как механизм экономии почти ничего не экономит — стоит либо признать это осознанно, либо расширить.
2. **Ключ кэша не содержит provider/model** (`response_cache.py:42–50`), а кэш — глобальный синглтон, разделяемый всеми клиентами (`get_llm_cache`, `instrumented.py:28`). Один и тот же RAG-вопрос, заданный после runtime-переключения модели (`set_llm_config`), в течение 5 минут вернёт ответ **прежней** модели (F-07).

*Мелочь:* `LLMResponseCache` заявлен «thread-safe via dict operations» — для asyncio это верно (нет await между чтением/записью), но eviction `next(iter(self._store))` удаляет произвольную (инсершен-первую), а не самую старую по TTL запись — некритично.

### A14. Оркестрация инкрементального тика

**Что делает и где.** `scheduler_service.py`: `run_incremental_for_all_sources` — параллелизм 2 источника (`scheduler_max_concurrent_sources`), пер-source advisory-lock и watchdog 1800s; `_process_source` — пайплайн + цепочка хуков; degraded-детекция (fail-ratio ≥ 0.5); хуки F5-C/F11/реконсиляция изолированы от `stage_errors` (сбой хука не валит тик).

**Оценка.** Архитектура хуков и изоляция сбоев — сильная сторона. Два дефекта производительности в одном месте:

```296:296:tg_parser/services/scheduler_service.py
            docs_before = await task_processed_repo.list_by_channel(channel_id)
```

```496:500:tg_parser/services/scheduler_service.py
                new_doc_refs = [
                    d.source_ref
                    for d in docs_after
                    if d.source_ref not in {dd.source_ref for dd in docs_before}
                ]
```

1. **O(N²):** set `{dd.source_ref for dd in docs_before}` строится заново для каждого `d` из `docs_after` (генератор в условии list-comprehension выполняется на каждой итерации). На канале с 10K документов это 100M операций построения множеств — секунды-десятки секунд чистого CPU на каждый тик каждого канала.
2. **Два полных корпусных SELECT'а** (`:296`, `:378`) с полным текстом документов ради вычисления разности `source_ref`'ов. В репозитории уже есть `list_source_refs_by_channel` (`processed_document_repo.py:275–280`), возвращающий только ref'ы; ещё лучше — один запрос `WHERE processed_at > :tick_start` или возврат новых ref'ов из самого пайплайна (он их знает).

`len(docs_after)` также используется для coverage (`:467`) — заменяется на существующий `count_by_channel`.

## 5. Предложения по оптимизации

### O-1. Передавать текст документов в ре-суммаризацию (закрывает F-02)
- **Что:** в `items_payload` добавить `summary` (и/или `text_clean` с усечением ~400–600 символов) каждого элемента окна; батчевый фетч через уже существующий `processed_doc_repo.get_by_source_refs`. Скорректировать `prompts/resummarize.yaml` (описание входа).
- **Эффект:** фича начинает выполнять назначение; рост input-токенов умеренный (10 элементов × ~150 токенов ≈ +1.5K на вызов, в пределах существующего 50K/тик бюджета).
- **Стоимость:** **S** — один сервис + один YAML; контракты/миграции не трогаются; тесты `resummarization` дополняются проверкой payload. Риск низкий (advisory-lock и версионирование уже есть).
- **Вердикт: Делать сейчас.** Максимальный эффект качества за минимальную цену.

### O-2. Пре-LLM дедуп по хэшу сырого текста (закрывает F-01)
- **Что:** перед LLM-вызовом считать `compute_content_hash(message.text)` (нормализация из `hashing.py` как есть) и проверять `find_by_content_hash` по каналу; при совпадении — записывать документ-дубль без LLM (или скип с метрикой). Существующий post-LLM дедуп сохранить (ловит вариации форматирования).
- **Эффект:** −1 полный processing-вызов на каждый точный репост; в пересекающемся кластере каналов — единицы-десятки процентов processing-бюджета.
- **Стоимость:** **S/M** — `pipeline.py` (2 пути), метрика, тесты дедупа; решение «скип vs синтетический документ» затрагивает провенанс (обсудить: дубль должен остаться прослеживаемым — предпочтителен вариант «копировать поля существующего документа с новым source_ref», как уже делает post-LLM ветка `:479+`).
- **Вердикт: Делать сейчас.**

### O-3. Починить тик планировщика (закрывает F-03)
- **Что:** (а) построить `before_refs = set(...)` один раз до цикла — минимальный фикс O(N²); (б) заменить оба `list_by_channel` на `list_source_refs_by_channel` (метод уже существует) и `count_by_channel` для coverage; (в) опционально — брать новые ref'ы прямо из результата пайплайна.
- **Эффект:** O(N²) → O(N); минус два полнокорпусных SELECT'а с текстами на каждый тик каждого канала. На больших каналах — секунды с тика.
- **Стоимость:** **S** — один файл, поведенчески эквивалентно; существующие тесты тика покрывают. Риск минимален.
- **Вердикт: Делать сейчас.** Вариант (а) — вообще однострочный.

### O-4. Тематические эмбеддинги в линковке и консолидации (закрывает F-04, частично F-05)
- **Что:** в `topic_linking_service.link_topics` и `_finalize_full_run` использовать topic-эмбеддинги (`run_topic_embedding` / topic_embedding_repo) вместо эмбеддинга первого якоря; фетчить батчево (`get_many_by_source_refs`-аналог). Fallback на якорный эмбеддинг при отсутствии тематического.
- **Эффект:** метрика похожести тем начинает измерять темы; порог 0.3 можно осмысленно калибровать; попутно −N+1 запросы.
- **Стоимость:** **M** — два сервиса, нужно гарантировать актуальность topic-эмбеддингов перед линковкой (порядок хуков), перекалибровка порога по данным (мини-симуляция в стиле ADR-0010). Риск средний: изменится состав линков — нужен snapshot-сравнительный прогон.
- **Вердикт: Делать сейчас** (после O-1..O-3): это главный рычаг качества cross-channel части.

### O-5. Top-k агрегация в инкрементальном assign (закрывает F-10)
- **Что:** перенести схему ADR-0010 (top-k, K=3, knob для отката на mean) из watchlist в `assign_documents_to_topics`.
- **Эффект:** больше документов матчится дёшево на Phase 1 → меньше документов в платный LLM-discover; выравнивание поведения тем с богатым словарём. Порядок: −10–30% discover-вызовов (оценка по аналогии с симуляцией ADR-0010, требует своей проверки).
- **Стоимость:** **S/M** — одна функция + настройка + тесты; риск сдвига покрытия тем — смягчается knob'ом отката.
- **Вердикт: Делать сейчас**, с read-only симуляцией на корпусе перед включением (процесс у проекта уже отработан).

### O-6. Кэш LLM: model в ключе (закрывает F-07, частично F-06)
- **Что:** добавить `provider`/`model` в `_make_key` (или держать кэш per-client). Расширение кэша на `generate_with_usage` — **не** делать: одинаковые промпты в пайплайне редки, а скрытие usage-токенов от учёта исказит метрики и rate-limiter.
- **Эффект:** устранение отдачи ответов чужой модели после runtime-переключения.
- **Стоимость:** **S** — один файл + тест. Риска нет.
- **Вердикт: Делать сейчас.**

### O-7. Токенизировать документ один раз на тик (закрывает F-08)
- **Что:** в `check_interests`/`backfill` строить `doc_tokens_by_ref` один раз и передавать в `compute_watch_score` (параметр с fallback на внутренний вызов — сигнатура остаётся совместимой).
- **Эффект:** O(I×D) → O(D) лемматизаций; на 20 интересах — до ×20 меньше CPU скоринга.
- **Стоимость:** **S** — один сервис, чистый рефакторинг, скоры байт-в-байт те же (легко утверждается тестом).
- **Вердикт: Делать сейчас.**

### O-8. Батчевые проверки существования и хэшей (закрывает F-09, часть A2)
- **Что:** в `_process_batch_parallel` заменить цикл `exists()` на один `get_by_source_refs` (или вовсе убрать — выборка уже фильтрует `NOT EXISTS`, оставить проверку только для не-tick путей); в `_filter_duplicates` — батчевый `find_by_content_hashes(channel_id, [...])`.
- **Эффект:** −до 300 запросов/тик/канал; чанковый дедуп — 1 запрос вместо 20.
- **Стоимость:** **S/M** — pipeline + новый метод репозитория; риск гонки «двойная обработка» уже закрыт advisory-lock'ом пайплайна.
- **Вердикт: Делать позже** — чистая экономия round-trip'ов, не блокирует ничего.

### O-9. Переиспользование клиентов (закрывает F-11)
- **Что:** поднять создание LLM-клиента из `resummarize_topic` в `run_for_channel` (один клиент на тик); для retrieval — модульный кэшированный embedding-клиент (или клиент на время жизни запроса API).
- **Эффект:** минус сокет/handshake на вызов; десятки мс на RAG-запрос.
- **Стоимость:** **S** для resummarize; **M** для retrieval (жизненный цикл/закрытие клиента в вебе). Риск утечек клиентов при небрежном lifecycle.
- **Вердикт: resummarize — делать сейчас (тривиально); retrieval — делать позже.**

### O-10. Merge: выбор представителя и защита от потери тем (закрывает F-12, F-13)
- **Что:** primary = член группы с максимумом якорей (или объединение scope_in/keywords); темы, не попавшие ни в одну группу, добавлять как синглтоны; `int(mid)`-коэрция со скипом некорректных ID вместо отката чанка.
- **Эффект:** нет молчаливой потери тем; метаданные слитой темы информативнее; меньше пересчётов чанков.
- **Стоимость:** **S/M** — одна функция + тесты крайних случаев ответа LLM.
- **Вердикт: Делать позже** (следующее окно работ по топикизации).

## 6. Альтернативные решения (архитектурный уровень)

1. **Эмбеддинг-кластеризация + LLM-нейминг вместо LLM-кластеризации полного корпуса (A5).** Документные эмбеддинги уже есть в pgvector. Кластеризация (agglomerative / HDBSCAN по cosine) даёт глобально связные кластеры за O(N log N)–O(N²) CPU без токенов; LLM вызывается один раз на кластер для title/summary/scope_in/scope_out (тот же формат TopicCard). Ожидаемо: LLM-вызовы O(topics) вместо O(docs/50) + merge — на канале 10K документов это ~50–200 вызовов вместо ~200 batch + merge, но главное — исчезает проблема «LLM видит окно в 50 документов» и весь merge-этап (A6) с его потерями. Стоимость: **XL** (новый модуль, паритет с чекпоинт-механикой, сравнительная оценка качества тем, миграция существующих карточек не нужна — можно катить на новых каналах). Целесообразность: **делать при следующем масштабировании** (новые крупные каналы / жалобы на качество тем); текущая resumable-механика делает статус-кво терпимым.
2. **ANN-поиск (HNSW) вместо all-pairs в линковке (A9) и как замена sliding-window в near-dup (A3 Phase 1).** pgvector поддерживает HNSW-индексы; для каждой темы/документа брать top-K соседей вместо полного перебора/окна last-N. O(T²)→O(T·log T); для near-dup убирает слепую зону окна (repost старше 50 сообщений). Стоимость: **M** (индекс + перезапись двух запросов). Целесообразность: **делать вместе с O-4** для линковки; для near-dup — при переходе ADR-0016 в Phase 1.
3. **Нормализация скоров vs RRF (A10) — не менять.** RRF безнормировочный и устойчивый; замена на weighted score normalization дала бы тонкую настройку, но потребовала бы калибровки на несравнимых распределениях ts_rank/cosine. Эффект/стоимость не в пользу замены.
4. **Дешёвая модель для processing коротких сообщений.** Runtime-переключение LLM по стадиям уже есть (`LLMConfigManager`); добавить маршрутизацию по длине (< ~200 символов → haiku/gemini-flash/ollama) — короткие реплики и комментарии не требуют sonnet-класса. Стоимость: **M** (маршрутизация в pipeline + оценка качества на выборке). Целесообразность: **делать позже**, после O-2 (пре-LLM дедуп сначала уберёт бесплатную часть потерь).
5. **Инкрементальная топикизация на базе topic-эмбеддингов вместо keyword-assign (A7).** Phase 1 мог бы матчить новые документы cosine'ом против topic-эмбеддингов (порог), keyword — как tie-breaker. Убирает denominator-penalty класс проблем целиком. Стоимость: **L** (перекалибровка покрытия, симуляция). Целесообразность: **делать позже**, после O-4/O-5 — сначала дешёвые фиксы той же оси.
