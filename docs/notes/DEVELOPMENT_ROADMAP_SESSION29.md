## Принципы приоритизации

1. **Сначала полнота данных** — прежде чем строить способы потребления (RAG, UI), нужно обеспечить полноту и актуальность исходных данных
2. **Telegram-канал ≠ документ** — канал содержит сотни слабосвязанных сообщений на подтемы одной большой области; десятки тем из 1000+ сообщений — это нормальная гранулярность для навигационной карты
3. **YAGNI** — не строить абстракции без второй реализации; оставшиеся INFO-зависимости (concrete repos вместо ports) устраняются когда появится реальная потребность

## Очерёдность фич

### P1: Инкрементальная обработка (Session 30)

**Цель:** Система сама подхватывает новые сообщения и обрабатывает их без ручного вмешательства.

**Что есть:** `--mode incremental` в ingestion (использует `last_post_id`), APScheduler в api/, `poll_interval_seconds` в Source.

**Что нужно:** Scheduled pipeline (ingest → process → topicize) по расписанию для всех активных источников, автоматическая ретопикизация при новых документах, отслеживание состояния каждого запуска.

**Влияние:** Данные всегда актуальны. Система переходит из режима "ручной запуск" в режим "запустил и забыл".

---

### P2: Параллельная обработка (Session 31)

**Цель:** Ускорение processing через concurrency.

**Что есть:** `--concurrency` флаг в CLI (по умолчанию 1), rate limiter в `llm/factory.py`.

**Что нужно:** Адекватный default concurrency (3-5), батчевая отправка в LLM API, оптимизация pipeline для параллельных запросов.

**Влияние:** Обработка 1000+ сообщений за минуты вместо десятков минут.

---

### P3: Улучшение обработки комментариев (Session 32)

**Цель:** Полнота данных — исправление failures на комментариях, привязка комментариев к постам.

**Что есть:** 2 failure на `comment:154` и `comment:4057` (LLM не возвращает `text_clean`), комментарии хранятся как отдельные raw_messages с `thread_id`.

**Что нужно:** Robust parsing LLM-ответов для коротких/пустых комментариев, контекст родительского поста при обработке комментария, агрегация тредов.

**Влияние:** 100% обработка всех сообщений, более качественные summary для комментариев с контекстом.

---

### P4: Топикизация — fix bundles (Session 32-33)

**Цель:** Каждая тема содержит все релевантные документы, а не только anchor.

**Что есть:** 64 темы по 1 doc (только anchors в sources). TopicBundle содержит topic_id и ссылки на документы.

**Что нужно:** Проверить bundle building (возможно, баг в assignment), добавить метрику coverage (% документов, попавших хотя бы в одну тему).

**Влияние:** Темы становятся полноценными кластерами, а не просто заголовками.

---

### P5: RAG-интеграция (Session 33-34)

**Цель:** Векторный поиск по базе знаний, Q&A чат-бот по контенту каналов.

**Зависит от:** P1-P4 (полные, актуальные, качественно кластеризованные данные).

**Что нужно:** Embeddings (OpenAI/Anthropic), векторное хранилище (pgvector или ChromaDB), retrieval pipeline, Q&A endpoint.

**Влияние:** KB из файла на диске превращается в рабочий инструмент — можно задавать вопросы на естественном языке.

---

### P6: Веб-интерфейс / дашборд (Session 35+)

**Цель:** Визуализация результатов обработки.

**Что нужно:** Frontend (React/Vue/Streamlit), API endpoints для тем/документов/статистики, фильтрация, поиск.

---

### P7: Мульти-канальная аналитика (Session 36+)

**Цель:** Кросс-канальные темы, сравнение каналов, единая база знаний из нескольких источников.

---

### P8: Мониторинг и метрики (по необходимости)

**Цель:** Prometheus exporters, Grafana дашборды, алерты на ошибки LLM.
