## 2. Scope

**Входит:**

1. **Закрытая грамматика ссылок в `normalize_channel_id`.** Там единая точка правды: чтение, запись и сравнение должны давать одну форму. Отдельный хелпер «для add_channel» не делать — иначе `search_knowledge_base(channel_id="t.me/x")` и `add_channel("t.me/x")` снова разойдутся. Сводятся к `x`, и только они:
   - схема `https://`, `http://` или без схемы;
   - хост ровно `t.me` или `telegram.me`, с `www.` или без; сравнение хоста без учёта регистра;
   - путь `/x`, `/x/`, `/s/x` (веб-превью), `/x/<десятичный id поста>`;
   - хвост `?…` и `#…` отбрасывается;
   - `x` после разбора проходит обычный путь: `@`, кавычки, внешние пробелы снимаются, как сейчас. Сам `x` должен подходить под регулярку username, иначе это не ссылка на публичный канал.

   **Не URL-ввод не меняет семантику:** bare `x`, `@x` и числовые id (`^-?\d+$`, в том числе `-100…`) идут прежним путём — как сейчас нормализуются и, на путях записи, валидируются `validate_channel_username`. Что считать «URL-подобным» (наличие `/`, `:`, известного хоста или схемы), определить в сессии и зафиксировать тестами на обе стороны границы.

   **Всё остальное URL-подобное — отказ**, без попытки угадать: `telegram.dog`, `tg://resolve?…`, userinfo (`user@t.me`), порт, scheme-relative `//t.me/x`, percent-encoding в пути, лишние сегменты (`/x/123/extra`), недесятичный id поста, приватные `t.me/+HASH`, `t.me/joinchat/HASH`, `t.me/c/<id>/<msg>`, пустой путь `https://t.me/`, чужой хост (`evilt.me/x`, `t.me.example.com/x`). Расширять список можно только решением в сессии с тестом на каждую новую форму.
2. **Невалидный непустой ввод — типизированный отказ, и только он.** Сегодня `None` означает «фильтра нет» (§1): отклонённая ссылка, превращённая в `None`, на пути чтения снимет фильтр и расширит выборку. Строковый sentinel («значение, которое ни с чем не совпадёт») тоже нельзя: зарезервированного пространства имён у `channel_id` нет. Контракт: непустой **URL-подобный** ввод вне закрытой грамматики §2 п. 1 даёт `InvalidChannelUsername` — не `None` и не строку. Не URL-ввод сохраняет прежнюю семантику (§2 п. 1). Поверхность чтения превращает отказ в ошибку или в пустой scoped-ответ **до** RBAC и lookup; поверхность записи возвращает отказ. `None` остаётся только для `None` и пустого ввода. Как выразить это в API функции (исключение, отдельная функция для URL-ввода и т. п.) — решение сессии, записать в docstring модуля. Попутно: `advisory_lock.py` берёт `normalize_channel_id(channel_id) or channel_id` — при `None` откатывается на сырую строку; путь проверить.
3. **Инвентаризация всех внешних входов `channel_id` / `channel_ids` источников:** бот, MCP, HTTP API, CLI (§1). Таблица «поверхность × операция → нормализуется? → валидируется?» — артефакт сессии, в PR. Нормализация происходит до RBAC (`assert_channel_access`, сравнение с `allowed_channel_ids`), lookup, idempotency key, advisory lock и записи. Пути записи — `add_channel` (бот, MCP), подписки на дайджест и watchlist (бот, MCP, HTTP, CLI `digest add` / `watchlist add`), CLI `add-source`, workspace add source — дополнительно вызывают `validate_channel_username`. Паритет MCP и бота — класс BUG-093.
4. **Маршруты HTTP с `channel_id` в пути** (`GET /channels/{channel_id}/stats`): обычный path-параметр не захватывает `/`, так что `t.me/x` до кода нормализации не дойдёт — маршрутизатор ответит 404 раньше. Решение сессии, рекомендация — не расширять маршрут: path-маршруты принимают только канонический id, это записывается в docstring маршрута, а тест подтверждает, что URL-форма в пути даёт 404 / 422 без утечки данных. Альтернатива — query-параметр или `{channel_id:path}` с интеграционным тестом маршрутизации обеих URL-форм; двойной `//` после схемы в пути нормализуется прокси и клиентами непредсказуемо.
5. **CLI `add-source` (двойной ключ).** Зафиксировать в сессии: `channel_id` канонизируется и валидируется всегда. Если `source_id` передан — он остаётся ключом, как сейчас, и тест вызывает обе формы ссылки с одинаковым `source_id`. Если в сессии решено делать `source_id` по умолчанию равным `channel_id` — канонизировать оба и проверить отсутствие дубля. Выбор записать в PR.
6. **Идемпотентность** сохраняется: `normalize(normalize(x)) == normalize(x)` для всех форм. Модуль на этом держится (docstring).
7. **Ops: фантомы `Ye_Ale`** — объём выбирает владелец в сессии:
   - **(a)** удалить две строки `sources` жёстко: данных под ними нет, `audit_log` остаётся;
   - **(b)** оставить: после R14 они невидимы, после R15 недостижимы.

   Рекомендация — (a): восстановить их уже нельзя, а в `sources` они продолжат путать ручные выборки. Процедура — §5 п. 6.

**Не входит:**

- модель владения каналом, в том числе «занят чужим владельцем» при повторном добавлении — отдельное обсуждение;
- **адрес доставки подписки** (`channel_id` / `target.channel_id`, §1): это чат получателя, а не источник; в инвентаризации указать его строкой «вне scope» с причиной;
- приведение регистра username (§1: разошлось бы с сохранёнными данными);
- четыре не-DF-4 soft-deleted строки admin;
- R16 / R18 / O1 / R17.

## 3. Ловушки

- **`None` = «без фильтра».** Самая опасная ошибка сессии — вернуть `None` для отклонённой ссылки (§2 п. 2). На `list_topics`, `search_knowledge_base`, `get_cross_channel_stats` это выдаст все доступные каналы вместо пустого ответа.
- **Порядок шагов в `normalize_channel_id` фиксирован** (docstring: внешние пробелы → кавычки → внутренние пробелы → `@` → хвост). Разбор URL встраивается так, чтобы `'  https://t.me/x  '` и `"@x"` давали одно и то же, а повторный вызов ничего не менял.
- **Не резать всё, что содержит `/`.** Жадное «взять последний сегмент» превращает `t.me/x/123` в `123` (числовой id!), а `t.me/+HASH` — в `+HASH`. Разбирать структуру ссылки, а не брать хвост.
- **Хост проверять целиком** (§2 п. 1): `evilt.me/x` и `t.me.example.com/x` — не Telegram.
- **Уже сохранённые id не должны сдвинуться ни на символ.** Нормализация участвует в ключе advisory lock, identity pipeline dispatch, Telethon-клиенте. Сдвиг канонической формы для существующего id = другой ключ блокировки = два параллельных прогона одного канала. Тест — §4.
- **Защита от плейсхолдеров.** `is_blocked_placeholder` смотрит на нормализованное значение. После R15 `t.me/test_channel` нормализуется в `test_channel` и обязан блокироваться так же, как `@test_channel`, в боте и MCP.
- **Парсер имени канала в боте** (`tests/test_bot_channel_name_parser.py`) и LLM. Gemini-агент может переписать ссылку до вызова инструмента. Контракт проверять на уровне executor'а (`_exec_add_channel` и др.), не промпта; тесты парсера прогнать после изменения нормализации.
- **`validate_channel_username` сейчас отвергает URL**, и тесты BUG-034 это, возможно, закрепляют. После R15 ссылка публичного канала из списка §2 п. 1 на этом пути — успех. Такие тесты переписать под новый контракт, не удалять; отказ остаётся для всего вне списка.
- **HTTP API — отдельный процесс и отдельный код маршрутов.** Нормализация в MCP / боте его не покрывает (§1).
- **Пересоздание стирает логи**, фаза тика сдвигается на «старт плюс интервал». После деплоя R14 фаза — `:02`, сверить в снимке. **Ждать конец тика по фиксированной строке:** `grep -F 'Incremental pipeline completed'`. Шаблон `Job "incremental_pipeline…executed` в JSON-логе не совпадает — кавычки экранированы (`\"`); в R14 это стоило получаса.
- **Бэкап — вне рабочей копии** (`/mnt/data/backups/tg_parser/…`, каталог `700`). `.gitignore` защищает только точное имя `.env`.
- **Два параллельных полных прогона** на одной `tg_parser_test` конфликтуют (`DROP SCHEMA`) — PR standard по очереди.

## 4. Тесты (минимум)

- **Таблица «форма → канон»** в `tests/test_utils_channel_id.py` или новом `tests/test_df4_tme_url_normalization.py`: каждая форма из §2 п. 1 даёт `x`; идемпотентность на каждой.
- **Таблица отказов:** каждая форма из «всё остальное» §2 п. 1 даёт `InvalidChannelUsername` — не `None` и не строку.
- **Не URL-ввод без изменений:** `AgeManagment`, `@AgeManagment`, `12345`, `-1002120019100` нормализуются и (на записи) валидируются как до R15. Граница «URL-подобного» покрыта тестами с обеих сторон.
- **Path-маршрут HTTP:** `GET /channels/{channel_id}/stats` с URL-формой ведёт себя по решению §2 п. 4 (рекомендация — 404 / 422 без данных).
- **Выборка не расширяется:** `list_topics` / `search_knowledge_base` / `get_cross_channel_stats` с `channel_id="t.me/+HASH"` (и одной чужой формой) возвращают ошибку или пустой ответ, а не результаты всех каналов — в MCP, боте, HTTP и CLI `search`.
- **Бит в бит для живых id:** нормализация каждого текущего прод-`channel_id` (список из снимка §1, числовые включительно) возвращает его без изменений. Ключ advisory lock и identity dispatch для канонических и числовых id не меняются.
- **Матрица по инвентаризации:** для каждой реально существующей пары «поверхность × операция» из таблицы §2 п. 3 — по тесту. Запись: для `https://t.me/x` — та же строка `sources` / те же `channel_ids`, что для `@x`, повторный вызов — update, не второй create; для инвайта — отказ. Чтение (`search`, `ask`, `list_topics`, channel stats, export, pipeline, process — где поверхность их имеет, CLI включительно): `channel_id="t.me/x"` видит и разрешает ровно то же, что `"x"`. Исключение — HTTP path-маршрут channel stats, для него действует §2 п. 4. Прецедент паритета — BUG-093.
- **Плейсхолдер:** `t.me/test_channel` блокируется в боте и MCP.
- **Парсер имени канала** в боте — существующие тесты зелёные, при необходимости добавить случай со ссылкой.
- Тест должен падать на текущем `main` — проверить через `git stash` правок `tg_parser/`, как в R14.
- **Полный PR standard** (`TEST_POSTGRES=1`) зелёный; ожидание — около 4.57k passed на 2026-09-25.
