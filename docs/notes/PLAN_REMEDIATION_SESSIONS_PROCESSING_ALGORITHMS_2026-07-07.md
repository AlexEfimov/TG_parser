## 0. TL;DR

- **7 сессий S1–S7.** Порядок: сначала Critical-дефект F-02 (сессия S1, размер S — максимум качества за минимальную цену), затем батч низкорисковых perf-фиксов (S2), затем стоимость LLM в processing (S3), затем два трека качества топикизации (S4 — topic-эмбеддинги, S5 — top-k assign; параллелизуемы), затем hardening merge (S6) и хвост «делать позже» + диспозиция Low-находок (S7).
- **Принцип упорядочивания:** (1) Critical и S-размерные «делать сейчас» — вперёд; (2) один subsystem — одна сессия (resummarize целиком в S1, pipeline-дедуп целиком в S3, merge целиком в S6), чтобы не платить за context-paging дважды; (3) фиксы с перекалибровкой порогов (S4, S5) — после дешёвых, с обязательной read-only симуляцией в стиле ADR-0010 до включения.
- **Не в плане (осознанно):** архитектурные альтернативы §6.1 (эмбеддинг-кластеризация, XL) и §6.5 (эмбеддинг-assign, L) — gated на масштабирование/данные S4–S5; батчинг сообщений в processing-вызов и кэш на `generate_with_usage` — вердикт отчёта «Не делать».
- Каждая сессия — focused, testable unit: свой прогон default + PR standard, поимённые тестовые файлы, метрики Prometheus/логи для верификации эффекта.

## 1. Сессии

### S1 — Ре-суммаризация получает текст документов (F-02 Critical)

- **Scope:**
  - **O-1** (закрывает **F-02**, Critical): передавать `summary` (и/или усечённый `text_clean` ~400–600 символов) элементов окна в `items_payload`; батчевый фетч через существующий `ProcessedDocumentRepo.get_by_source_refs` (порт `storage/ports.py:534`, impl `processed_document_repo.py:163` — SELECT уже возвращает `text_clean`/`summary`, новый метод не нужен); скорректировать `prompts/resummarize.yaml` (описание входа). Файлы: `tg_parser/services/resummarization_service.py:277–285`, `prompts/resummarize.yaml`.
  - **Проводка (уточнение scope 2026-07-07, шире, чем в исходной оценке — но всё ещё низкий риск, без схемы/контрактов):** `ResummarizationService.__init__` не принимает processed-doc-репозиторий, а контекст-менеджер `resummarization_repos()` (`services/db_context.py:337–358`) не отдаёт его. Нужно расширить этот context manager (в той же processing-сессии) и обновить **все 6 мест позиционной распаковки его кортежа**. Из них **3 конструируют сервис** (сюда прокидывается новый repo): `scheduler_service.py:1158–1168`, `mcp_server.py:2540–2550` (force_resummarize), `cli/topic_cmd.py:143–153`. Ещё **3 только распаковывают кортеж** (сервис не строят, но сломаются при изменении арности): `mcp_server.py:2481` (get_topic_versions), `cli/topic_cmd.py:41` (versions), `cli/topic_cmd.py:120` (resummarize --dry-run).
  - **O-9a** (часть **F-11**): поднять создание LLM-клиента из `resummarize_topic` в `run_for_channel` — один клиент на тик. Ограничение: `resummarize_topic` вызывается напрямую (минуя `run_for_channel`) из MCP `force_resummarize` (`mcp_server.py:2552`) и CLI (`cli/topic_cmd.py:155`), поэтому подъём клиента должен сохранить fallback-путь (опциональный параметр клиента); обновить устаревший docstring `aclose()`.
  - **Out of scope:** O-9b (retrieval-клиент — S7); любые изменения триггеров/лимитов ре-суммаризации (счётчик N=5, 10 тем/тик, 50K токенов/тик — не трогаем); контракты и миграции.
- **Rationale / порядок:** единственный Critical; отчёт (§5 O-1): «максимальный эффект качества за минимальную цену». Размер S, риск низкий (advisory-lock и версионирование уже есть), зависимостей нет — идёт первым. Каждый день промедления — впустую сожжённые вызовы (до 10 × 4096 max_tokens на тик на канал).
- **Deliverable:** F5-C начинает выполнять назначение — сводки тем реально обогащаются содержанием новых документов; рост input-токенов умеренный (~+1.5K на вызов, в пределах бюджета 50K/тик); минус httpx-handshake на каждую тему.
- **Test strategy:**
  - Режимы: *default* обязателен; *PR standard* (`TEST_POSTGRES=1`) — затронут repo-фетч.
  - Существующие: `tests/test_f5c_resummarization_service.py`, `tests/test_resummarize_metrics.py`, `tests/test_f5c_scheduler_hook.py`, `tests/test_f5c_counter_increment.py`, `tests/test_f5c_topic_card_repo.py`, `tests/test_prompt_loader.py` (валидность YAML после правки).
  - Новые: assert на состав payload (каждый item содержит `summary`/`text_clean`, усечение работает); тест «клиент создаётся один раз на `run_for_channel`».
  - Ручная/метрики: сравнить input_tokens ре-суммаризации до/после (метрики resummarize из `test_resummarize_metrics.py`-инструментария; лог одного реального прогона на dev-канале) — рост в ожидаемых пределах, сводка содержит факты из новых документов.
- **Размер/риски:** **S** (поверхность файлов шире, чем в исходной оценке — +`db_context.py` и 6 мест распаковки кортежа `resummarization_repos()` — 3 конструктора + 3 чистых распаковки, — но это механическая проводка без изменения схемы/контрактов, риск остаётся низким). Риск: рост токенов на длинных окнах — контролируется усечением per-item и существующим бюджетом 50K/тик; регресс standalone-вызовов `resummarize_topic` — закрыт fallback-параметром клиента и тестами.

  - **O-6** (закрывает **F-07**, частично F-06): добавить `provider`/`model` в `_make_key` глобального TTL-кэша. Файлы: `tg_parser/processing/llm/response_cache.py:42–50`, `instrumented.py`.

Идёт до S4: S4 меняет порядок хуков в том же `scheduler_service.py` — сначала чиним его горячий путь, чтобы S4 ложился на чистую базу.   - Ручная/метрики: длительность тика в логах/Prometheus на dev-канале до/после; отсутствие изменений в watch_matches на фикстурном прогоне.
- **Размер/риски:** **S** (сумма трёх S). Риск минимальный — все три фикса поведенчески эквивалентны по результату; главный риск — регресс порядка `new_doc_refs` (покрывается тестом).

### S3 — Пре-LLM дедуп и батчевые проверки в pipeline (F-01, F-09)

- **Scope:**
  - **O-2** (закрывает **F-01**, High): до LLM-вызова считать `compute_content_hash(message.text)` (нормализация из `domain/hashing.py` как есть) + `find_by_content_hash` по каналу; при совпадении — вариант «копировать поля существующего документа с новым source_ref» (как post-LLM ветка `pipeline.py:479+`), провенанс сохраняется; метрика hit'ов. Post-LLM дедуп сохраняется (ловит вариации форматирования). Файлы: `tg_parser/processing/pipeline.py` (оба пути: `process_message`, `_process_batch_parallel`).
  - **O-8** (закрывает **F-09** + батчинг A2): убрать/заменить цикл `exists()` (`pipeline.py:1200–1204`) — выборка уже фильтрует `NOT EXISTS`; в `_filter_duplicates` — батчевый `find_by_content_hashes(channel_id, [...])` (новый метод репозитория). Вердикт отчёта — «позже», но включаем сюда по принципу «один subsystem — одна сессия»: обе правки в дедуп-пути `pipeline.py`, тесты общие.
  - **Out of scope:** второй raw-hash в схеме/контрактах как отдельное персистентное поле — только если реализация потребует (обсудить в сессии); дешёвая модель для коротких сообщений (§6.4 — после этой сессии, отдельным треком); near-dup Phase 1 (ADR-0016 — свой gate).
- **Rationale / порядок:** главная утечка токенов (High): каждый точный репост = оплаченный processing-вызов ~2–4K токенов, при 916 cross-channel keyword-overlaps на 10 каналах — регулярные потери. После S1/S2, потому что дороже (S/M) и требует решения по провенансу дублей; до §6.4 (дешёвая модель), потому что сначала надо убрать бесплатную часть потерь (порядок явно рекомендован отчётом).
- **Deliverable:** точные репосты/форварды не доходят до LLM: −1 полный processing-вызов на каждый точный дубль (единицы–десятки процентов processing-бюджета в пересекающемся кластере); −до 300 лишних `exists()`-запросов/тик/канал; чанковый дедуп — 1 запрос вместо 20; новая метрика pre-LLM dedup hits.
- **Test strategy:**
  - Режимы: *default* + *PR standard* (новый repo-метод `find_by_content_hashes` — PG-gated); перед merge — *max local* (E2E-путь).
  - Существующие: `tests/test_processing_pipeline.py` (основной), `tests/test_e2e_pipeline.py`, `tests/test_storage_integration.py`, `tests/test_near_duplicate_observe.py` (near-dup hook не задет), `tests/test_metrics_instrumentation.py`.
  - Новые: пре-LLM дедуп — точный репост не порождает LLM-вызов (mock-LLM assert call-count), документ-дубль прослеживаем (source_ref новый, поля скопированы); идемпотентность повторного тика; батчевый `find_by_content_hashes` (пустой список, частичные совпадения, cross-chunk).
  - Ручная/метрики: счётчик pre-LLM dedup hits в Prometheus; на dev-прогоне канала с известными форвардами — снижение processing-вызовов в логах rate-limiter'а.
- **Размер/риски:** **S/M**. Риски: решение «скип vs синтетический документ» затрагивает провенанс (решение зафиксировано выше — копирование полей); ложные срабатывания raw-hash маловероятны (SHA-256 точного совпадения), гонка закрыта advisory-lock'ом пайплайна.

### S4 — Тематические эмбеддинги в линковке и cross-chunk консолидации (F-04, F-05)

- **Scope:**
  - **O-4** (закрывает **F-04**, High; частично **F-05**): в `topic_linking_service.link_topics` (`:104–112`) и `topicization_service._finalize_full_run` использовать topic-эмбеддинги (`run_topic_embedding` / topic_embedding_repo) вместо эмбеддинга документа первого якоря; батчевый фетч (аналог `get_many_by_source_refs`) — закрывает N+1 из F-05; fallback на якорный эмбеддинг при отсутствии тематического; гарантировать актуальность topic-эмбеддингов перед линковкой (порядок хуков в scheduler); перекалибровка `cross_channel_link_threshold=0.3` мини-симуляцией в стиле ADR-0010 + snapshot-сравнительный прогон состава линков.
  - **Опционально (stretch, решение внутри сессии по масштабу):** §6.2 — HNSW-индекс + top-K KNN вместо all-pairs O(C²·T²) (остаток F-05). Отчёт рекомендует «делать вместе с O-4»; если сессия выходит за M — вынести в отдельную S4b.
  - **Out of scope:** near-dup ANN (вторая половина §6.2 — gated на ADR-0016 Phase 1); §6.1 эмбеддинг-кластеризация (XL, отдельное решение при масштабировании); изменение самой метрики cosine+Jaccard.
- **Rationale / порядок:** последний High; «главный рычаг качества cross-channel части» (§5 O-4). После S1–S3, как явно предписывает отчёт («после O-1..O-3»): размер M, средний риск (изменится состав TopicLink), нужна калибровка. После S2 ещё и потому, что трогает порядок хуков в уже починенном `scheduler_service.py`.
- **Deliverable:** похожесть тем измеряет темы, а не два случайных поста; порог 0.3 перекалиброван по валидной метрике (data-driven, симуляция задокументирована); −N+1 фетчи эмбеддингов; snapshot-diff состава линков до/после приложен как артефакт сессии.
- **Test strategy:**
  - Режимы: *default* + *PR standard* (pgvector-запросы — PG-gated).
  - Существующие: `tests/test_topic_linking_service.py` (основной), `tests/test_cross_channel_topicization.py`, `tests/test_embedding.py`, `tests/test_topicization.py` (finalize-путь), `tests/test_scheduler_service.py` (порядок хуков).
  - Новые: fallback-ветка (нет topic-эмбеддинга → якорный); батчевый фетч; тест порядка хуков (topic-embedding до линковки).
  - Ручная/метрики: read-only симуляция порога на реальном корпусе (10 каналов, ~1000 тем) с отчётом-артефактом; сравнение avg-sim линков с baseline 0.33 (ADR-0016); длительность link_topics в логах.
- **Размер/риски:** **M** (с §6.2 — до M+M, тогда сплит на S4b). Ключевой риск — сдвиг состава линков: митигируется snapshot-прогоном и калибровкой до включения; средний риск по отчёту.

### S5 — Top-k агрегация в инкрементальном assign (F-10)

- **Scope:**
  - **O-5** (закрывает **F-10**): перенести схему ADR-0010 (top-k, K=3, knob отката на mean) из watchlist в `assign_documents_to_topics` (`processing/topicization.py`); настройка + knob; **обязательная read-only симуляция на корпусе до включения** (процесс отработан в ADR-0010).
  - **Out of scope:** §6.5 (эмбеддинг-based assign, L) — следующая итерация той же оси, gated на результаты S4+S5; программная пост-проверка similarity в discover (замечание A7 — не имеет ID-находки, зафиксировать в backlog S7).
- **Rationale / порядок:** качество+стоимость сразу (меньше документов уходит в платный LLM-discover, оценка −10–30% discover-вызовов). Требует симуляции — поэтому после дешёвых S1–S3. **Параллелизуема с S4** (разные функции: assign vs linking/finalize), но обе — ось топикизации; при solo-исполнении рекомендуемый порядок S4 → S5 (S4 закрывает High).
- **Deliverable:** больше документов матчится дёшево на Phase 1; выравнено поведение тем с богатым словарём (denominator penalty закрыта тем же способом, что в watchlist); knob позволяет мгновенный откат; отчёт симуляции — артефакт сессии.
- **Test strategy:**
  - Режимы: *default*; *PR standard* при затрагивании repo-путей.
  - Существующие: `tests/test_incremental_topicization.py` (основной), `tests/test_topicization.py`, `tests/test_bug075_topicization_reconciliation.py` (реконсиляция покрытия не сломана).
  - Новые: unit на top-k агрегацию скора (K=3, кейсы из ADR-0010: богатый словарь vs бедный); тест knob'а отката (mean-режим воспроизводит старое поведение).
  - Ручная/метрики: симуляция на корпусе (доля Phase-1-матчей до/после, ожидание −10–30% discover); счётчик discover-вызовов в метриках за несколько тиков после включения.
- **Размер/риски:** **S/M**. Риск сдвига покрытия тем — смягчён knob'ом и симуляцией до включения.

### S6 — Merge-hardening топикизации (F-12, F-13)

- **Scope:**
  - **O-10** (закрывает **F-12**, **F-13**): в `_merge_topics` (`processing/topicization.py:1393–1548`) — primary = член группы с максимумом якорей (или объединение scope_in/keywords); темы, не упомянутые LLM ни в одной группе, добавляются как синглтоны (нет молчаливой потери); коэрция `int(mid)` со скипом некорректных ID вместо отката целого чанка.
  - **Out of scope:** F-17 (truncation-сплит переотправляет батч — Low, смягчён, диспозиция в S7); изменение промпта `merge.yaml` сверх необходимого; §6.1 (замена LLM-кластеризации целиком).
- **Rationale / порядок:** вердикт отчёта — «делать позже (следующее окно работ по топикизации)»; окно топикизации — это S4/S5, поэтому S6 сразу за ними: контекст subsystem'а ещё горячий, а изменения S6 (структура результата merge) не конфликтуют с S4/S5 (другие функции). Не раньше — не блокирует ничего и не High.
- **Deliverable:** нет недетерминированной потери тем при неполном ответе LLM; метаданные слитой темы информативнее; один кривой ID больше не откатывает чанк (меньше пересчётов и потерянных merge-токенов).
- **Test strategy:**
  - Режимы: *default* достаточен (unit-уровень); *PR standard* перед merge.

## 2. Граф зависимостей / сводка порядка

```
S1 (F-02, Critical, S)  ──┐
S2 (F-03/F-07/F-08, S)  ──┼──►  S4 (F-04/F-05, M)  ──►  S6 (F-12/F-13, S/M)  ──►  S7 (хвост, M)
S3 (F-01/F-09, S/M)     ──┘         ‖ (параллелизуемо)
                                 S5 (F-10, S/M)
```

- **S1, S2, S3 взаимно независимы** — могут идти в любом порядке и параллельно (разные файлы: resummarization / scheduler+watchlist+cache / pipeline). Рекомендуемый порядок при solo-исполнении: S1 → S2 → S3 (Critical первым; S2 однострочно-дёшев; S3 требует решения по провенансу).
- **S4 блокируется S2** (мягко): S4 меняет порядок хуков в `scheduler_service.py`, который S2 чинит; отчёт также явно предписывает O-4 «после O-1..O-3».
- **S5 параллелизуема с S4** (разные функции топикизации), но при solo — после S4.
- **S6 после S4/S5** — то самое «следующее окно работ по топикизации» из вердикта O-10; жёсткой зависимости нет.
- **S7 последним** — сборный хвост без блокировок.
- Жёстких (код-уровневых) зависимостей всего две: S2→S4 (scheduler-хуки) и логическая пара S4/S5→§6.5 (за пределами плана).

## 3. Приоритизация — обоснование сквозного порядка

1. **Critical вперёд при цене S:** F-02 — фича F5-C не выполняет назначение и жжёт токены каждый тик; фикс — один сервис + один YAML. Нет причин, по которым что-либо должно идти раньше.
2. **Quick-wins с высоким ROI вытянуты вперёд (S2):** F-03 (High, фикс фактически однострочный + замена двух вызовов на существующие методы), F-07 и F-08 — S-размерные, нулевой/минимальный риск, поведенческая эквивалентность. Дёшево покупаем скорость тика и корректность кэша до любых структурных правок.
3. **High по стоимости (F-01) третьим:** дороже S1/S2 (S/M, решение по провенансу), но это главная утечка LLM-бюджета processing — до конца «дешёвого» блока.
4. **High по качеству (F-04) — после дешёвого блока:** M-размер, средний риск, требует перекалибровки порога и snapshot-прогона; отчёт явно ставит его «после O-1..O-3».
5. **Калибруемые изменения (S4, S5) — только через read-only симуляцию** до включения — процесс, отработанный проектом в ADR-0010; риск сдвига поведения гасится данными, а не угадыванием.
6. **«Делать позже» (O-8, O-10, O-9b) не выброшены, а поставлены в места максимальной когерентности:** O-8 — в S3 (тот же дедуп-путь pipeline), O-10 — в S6 сразу за окном топикизации S4/S5, O-9b — в S7.
7. **Batched-by-subsystem:** resummarize (S1), scheduler/watchlist/cache (S2), pipeline-дедуп (S3), cross-channel топикизация (S4), assign (S5), merge (S6) — ни один subsystem не размазан по нескольким сессиям.
