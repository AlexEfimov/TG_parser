## 3. Метод — восемь проходов, в этом порядке

Ревью 9.6k строк «сверху вниз» не работает; работают направленные проходы, каждый со своей таблицей на выходе.

### P0 — Инвентарь поверхности (генерируется, не пишется руками)

Две таблицы в артефакт:

- **bot (35):** имя → read/write → в `_WRITE_TOOLS_REQUIRING_CONFIRM`? → в `_PAGINATED_READ_TOOLS`? → в `_READ_TOOLS_TRACKED_FOR_CONTEXT`? → executor.
- **MCP (47):** имя → read/write → admin-only? → какой access-check (`assert_channel_access` / `assert_topic_access` / owner-scoped запрос / **нет**) → принимает `workspace_id`? → пагинация.

Классификаторные множества: `_WRITE_TOOLS_REQUIRING_CONFIRM` (`tools.py:110`), `_READ_TOOLS_TRACKED_FOR_CONTEXT` (`:172`), `_PAGINATED_READ_TOOLS` (`:191`), `_TOOL_EXECUTORS` (`:4981`). Якоря на дату подготовки; при дрейфе — искать по символу.

### P1 — Ownership / authz sweep (класс BUG-093)

Для **каждого** инструмента из P0: где стоит проверка доступа, стоит ли она **до** первого чтения/записи данных, и одинакова ли на двух поверхностях. BUG-093 существовал потому, что check стоял на ветке create и отсутствовал на ветке update того же инструмента — искать именно ветвления, где check обходится. Особое внимание: admin-инструменты (`register_user`, `update_user`, `add/remove_user_auth`, `list_users`, `list_all_workspaces`, `force_resummarize`, `reload_prompts`, `set/reset_llm_config`), у которых прогона в #1 не было (`not_run`).

### P2 — Write-shape sweep (класс BUG-094)

Для каждого write-инструмента: какой объект он строит, полным или частичным upsert'ом пишет, и что молча затирается дефолтами при «обновлении». Кандидаты: `subscribe_digest` / `subscribe_watchlist` (upsert или insert?), `update_user`, workspace-операции, `set_llm_config`.

### P3 — Parity bot ↔ MCP

Для инструментов, существующих на обеих поверхностях (большинство из 35): расходятся ли дефолты, лимиты, видимость, форма ошибок. Прецедент дрейфа уже есть: `list_digests` / `list_watchlists` дублируют payload (`subscriptions`/`interests` **и** `items` — `tools.py:4281`, `:4800`; #1 намерила 44.4 КБ на 24 интереса).

### P4 — Адреса, подтверждённые прогоном (#1) и сверкой (#2)

Стартовые точки с готовыми доказательствами — разобрать каждую до кода:

| # | Адрес | Якорь |
|---|---|---|
| 1 | Экспорт MCP: файл пишется в свой контейнер, `download_url` указывает в чужой; `file_path` без `job_id` (BUG-096) | `mcp_server.py` export-инструменты; сравнить с `api/routes/export.py` |

### P5 — Privacy / логирование

Прецеденты BUG-087 (deny-list на tool args) и BUG-088 (closed-vocabulary verdict вместо free text) закрыли два call-site. Свип: все остальные log-вызовы в обоих файлах — уходит ли в лог свободный текст пользователя, значения аргументов, результаты инструментов; `redact_tool_args` применён везде, где надо; не эхо-ится ли пользовательский ввод в сообщениях об ошибках; `raw_payload` недостижим через каждый read-инструмент (в #1 проверены `get_document` и экспорт — остальные пути только статически).

### P6 — Concurrency / state

Пагинационные курсоры и их жизнь в FSM (сторона tools.py); идемпотентность write-инструментов при повторе; advisory-lock паттерн `force_resummarize` (`status='locked'`); гонка «две сессии, один `output/raw_messages.json`» (уже BUG-096 — здесь проверить, нет ли того же паттерна у других файловых операций); dispatch долгих операций (`trigger_*` — HTTP-прокси: таймауты, обработка неответа).

### P7 — Дрейф деклараций и контрактов

Схемы `TOOL_DECLARATIONS` (типы, ranges, enum, required) против фактической валидации в executor'ах; result-модели MCP против `docs/contracts/*.schema.json`, где применимо; пагинационный контракт (тесты `test_mcp_pagination_contract.py`, `test_pagination_contract_tdd.py` — прогнать, они дёшевы); ADR-0004: `rg`-проверка, что bot не импортирует внутренности `api` и наоборот; ADR-0007: путь авторизации MCP (`resolve_current_user`, `mcp_server.py:457`) соответствует принятой схеме.

## 4. `handlers.py` — условие подключения

По DECISION: подключается, только если (a) #1 дал fail/partial на **живом** bot UX — не дал: колонка bot заполнялась по декларациям, — или (b) находка High/Critical в двух обязательных файлах требует контекста handlers (например, механизм обхода confirm-flow продолжается в диспетчере).

**Правило:** триггер (b) фиксируется в артефакте явной строкой «handlers.py подключён из-за F-NN»; ревьюируются **только пути, вовлечённые в находку**, не весь файл. Без триггера — строка «handlers.py не подключался: триггер не сработал».

## 5. Формат находки (Fable5)

```markdown
### F-NN (Severity — ось) — заголовок одним предложением, называющий дефект

| Поле | Значение |
|---|---|
| **Anchor** | символ + строка на <sha> |
| **Evidence** | цитата кода ≤10 строк / строка матрицы #1 / команда с выводом |
| **Verified** | что доказано; **Not verified:** что осталось гипотезой |
| **Impact** | чем это оборачивается для пользователя/оператора/денег |
| **Fix direction** | направление минимального фикса (не патч); отделить hardening |
| **Runtime check needed** | да/нет — что именно должна прогнать fix-сессия |
```

Severity: Critical / High / Medium / Low — по шкале BUG_LOG. Оси: correctness · authz · write-shape · parity · privacy · concurrency · contract-drift.

**Правила.** Каждое утверждение о поведении — из кода, теста или матрицы #1; чего нельзя доказать статически — помечать `needs runtime`, не утверждать. Находки, дублирующие заведённые BUG-095…098, не плодить — ссылаться и добавлять только новое (например, точный механизм). Не эссе: разбор длиннее 15 строк — признак, что находку надо резать на две или отправить часть в remediation-план.
