## 1. Почему эта сессия существует и почему она вперёд латентного High

Замер на проде 2026-08-13 (read-only, окно 2026-08-12 00:13 → 2026-08-13 17:01, ≈41 ч):

- попытки, помеченные отказом: **320**, в них **1108** документов и **1 495 164 токена**;
- попытки успешные: 240, в них **10** документов и 20 416 токенов;
- то есть **≈99 % токенов стадии processing** уходит в документы, которые тут же отбрасываются.

Но дорого не количество дубликатов, а **бессрочность**. В сохранившемся окне логов `tg_parser` (2026-08-13 15:00 → 17:01, три тика) 81 событие `dedup_db_duplicate` приходится на **27 уникальных** документов — каждый ровно **три раза**, документов, увиденных однажды, **ноль**. Те же 27 документов будут переобрабатываться и завтра.

Поэтому R11 вытащена вперёд R1 решением владельца: это единственная запись в очереди с постоянным расходом прямо сейчас, тогда как оба High из ревью латентны (эскалировать некого, пока не выпущен первый не-admin credential). В деньгах это порядок центов в сутки — не пожар; в токенах это 99 % стадии, и расход не прекратится сам.

## 2. Что установлено (не переоткрывать)

1. **Механизм цикла — прочитан из кода.** Нормальный путь выбирает работу через `raw_repo.list_unprocessed_by_channel` ([`raw_message_repo.py`](../../tg_parser/storage/sqlalchemy/raw_message_repo.py)) — это `NOT EXISTS` по `processed_documents`. Post-LLM дедуп (`_filter_duplicates`) строку **не пишет**, поэтому следующий тик снова видит документ необработанным. Докстринг `_build_dedup_mirror` говорит это прямым текстом: «Unlike the post-LLM dedup path (**which returns the existing doc and writes nothing**)…».
2. **Данные для фикса уже собраны в коде.** `_filter_duplicates` возвращает `dropped_to_canonical: dict[source_ref → канонический ProcessedDocument]` ([`pipeline.py`](../../tg_parser/processing/pipeline.py) ~1254–1327), и `_process_batch_parallel` уже поднимает его через `_persist_chunk` до самого верха (~1640–1735). R10 использует его размер как `_batch_post_llm_dedup`. Ничего дополнительно вычислять не нужно — нужно записать.
3. **Форма фикса имеет прецедент в этом же файле.** S3 (O-2) для pre-LLM дубликата **материализует строку-зеркало**: свой `source_ref`/`id`/`processed_at`, скопированные `text_clean`/`summary`/`topics`/`entities`/`language`/`content_hash`, провенанс `metadata['dedup_of']` и собственный `metadata['raw_content_hash']`. Помощники — `_build_dedup_mirror` (~1107) и `_persist_dedup_mirrors` (~1184); зеркала **намеренно** минуют `_filter_duplicates`, потому что делят `content_hash` с оригиналом.
4. **Тот же класс дефекта уже ловили — и это важнее всего остального, но читать прецедент надо точно.** `Bugbot follow-up #2 (2026-07-07)` в записи F-01/S3 описывает его дословно: within-tick repost, чей лидер был отброшен post-LLM дедупом, «counted as `_batch_pre_llm_deferred` **every tick, never persisted**, while the leader kept burning a full LLM call that was also discarded — **a permanent stuck loop + recurring cost**». Формулировка лежит в BUG_LOG месяц.
   **Что тогда починили — и почему это не тот же случай, что на проде.** Фикс протянул `dropped_to_canonical`, чтобы **repost** мирроровался против канонического документа. У repost'а и лидера сырой текст **один и тот же** (иначе repost не был бы пойман pre-LLM как within-tick дубликат), поэтому зеркало repost'а несёт **их общий** `raw_content_hash` — и на следующем тике уже сам лидер разрешается cross-tick pre-LLM, без вызова LLM. Комментарий в коде (~1716) говорит это прямо: «the mirror carries the raw hash, so the next tick the leader itself resolves cross-tick». То есть в **той** конфигурации цикл закрыт с обеих сторон.
   **Прод-цикл — это тот же класс в конфигурации без близнеца.** Одинокий документ, чей `text_clean` схлопнулся с уже существующей строкой, а сырой хэш не совпадает ни с чем (канонический документ — legacy без `raw_content_hash`, либо сырой текст просто другой). Ему никто не пишет строку: repost'а, который принёс бы его сырой хэш в БД, не существует. Отсюда 27 документов, каждый на каждом тике. **Ценность прецедента** в том, что форма фикса («материализовать строку») уже принята и обкатана, а класс дефекта уже назван — не в том, что код с июля не менялся.
5. **Три механизма, по которым дубликат минует pre-LLM проверку** (прочитаны в R10, порядок не менялся): нормализация LLM (разный сырой текст → одинаковый `text_clean`; до вызова не поймать в принципе); legacy-строки без `metadata['raw_content_hash']` (пишется только с S3, июль 2026); media-only и пустые сообщения (сырого хэша нет по построению, а синтетический `text_clean` массово коллизирует — но LLM для них **не вызывается**, то есть эта доля токенов не стоит).
6. **Половина (a) закрыта в R10.** У дедупа есть свой исход `deduplicated_count`, он исключён из `failed_count`, знаменатель `attempted` сохранён. Тесты R10 ([`tests/test_bug097_dedup_classification.py`](../../tests/test_bug097_dedup_classification.py)) — страховка: они должны остаться зелёными, и если фикс R11 их ломает, это разговор про смысл счётчиков, а не «поправь тест».

## 3. Scope — строго в этом порядке

### 3.1 Red/green первым: инвариант, которого нет

Ни один тест не утверждает, что **повторный тик не платит за то же самое**. Именно поэтому цикл жил незамеченным при зелёном CI: дедуп проверяется на *корректность* (дубликат отброшен), и это верно по обе стороны от LLM-вызова.

Красный тест: два тика подряд на одном и том же наборе сырых сообщений, где второй документ — дубликат первого по `text_clean`. Первый тик: LLM вызван N раз, дубликат отброшен. **Второй тик: LLM не вызван ни разу для отброшенного `source_ref`** — assert на call-count LLM-двойника, а не на счётчики. На текущем коде этот assert падает: мок получит тот же документ снова.

Второй красный: у отброшенного `source_ref` после тика **есть** строка в `processed_documents` (или иная запись, которая выводит его из `list_unprocessed_by_channel` — форма выбирается в §3.2, но проверка нужна на уровне «репозиторий больше его не отдаёт», иначе тест зафиксирует реализацию вместо инварианта).

Образцы для стиля: [`tests/test_s3_pre_llm_dedup.py`](../../tests/test_s3_pre_llm_dedup.py) (там же кейсы про legacy-строку и within-tick лидера), [`tests/test_f5a_phase3_dedup.py`](../../tests/test_f5a_phase3_dedup.py) (post-LLM дедуп), [`tests/test_bug097_dedup_classification.py`](../../tests/test_bug097_dedup_classification.py) (двойники репозиториев и LLM, уже написанные под этот участок).

### 3.2 Запись факта отбраковки — это и есть фикс

Ровно одна правка останавливает расход. Но **прежде чем выбирать форму, проверь, что тянет за собой новая строка** (§3.2.1) — от этого зависит выбор, и именно это отличает дешёвый фикс от переноса расхода из одной стадии в другую.

Три формы, выбрать в сессии и записать обоснование:

**(A) Сохранить сам отброшенный документ** с провенансом `metadata['dedup_of'] = canonical.source_ref` вместо того, чтобы его выбросить. Минимальная правка в `_persist_chunk` / `_filter_duplicates`. Плюс: LLM-вывод, за который уже заплачено, не теряется. Минус тонкий: `content_hash` считается только по `text_clean`, поэтому у совпавших документов **текст** одинаков, а `summary`, `topics` и `entities` — свои, полученные отдельным вызовом. То есть в БД окажутся два документа с одним текстом и, возможно, разными выводами модели; какой из них «правильный», система не знает.

**(B) Построить зеркало против канонического документа** через существующий `_build_dedup_mirror`. Плюс: форма провенанса одна и та же для pre-LLM и post-LLM дедупа, единственный источник истины для summary — канонический документ. Минус: `_build_dedup_mirror(message, original, raw_hash)` требует **сырое сообщение** и **сырой хэш**, а `_filter_duplicates` работает с `ProcessedDocument`; для media-only и пустых сообщений `_compute_raw_hash` возвращает `None`. То есть нужно либо протащить сырые сообщения в это место, либо разрешить зеркало без `raw_content_hash`.

**(C) Отдельная таблица-маркер отбраковки** + второй anti-join в `list_unprocessed_by_channel` (рядом с существующим анти-джойном `processing_failures`, который уже стоит там по BUG-069 Option A — то есть паттерн «второй источник исключений» в этом запросе принят). Плюс: **ноль побочных эффектов ниже по течению** (см. §3.2.1) — документ не становится «новым обработанным». Минус: миграция, новая сущность и правка того самого запроса, который BUG-069 делал аккуратным ради `pgsql_tmp`/DiskFull.

**Что решает выбор, а что нет.** Цикл останавливает **любая** запись, из-за которой ref перестаёт попадать в окно выборки — `NOT EXISTS` и `processed_repo.exists()` смотрят только на факт наличия. А `raw_content_hash` в записи — это уже второй эффект: с ним следующий **репост** того же сырого текста поймается pre-LLM и не будет стоить даже первого вызова. Форма (C) этого второго эффекта не даёт, если хэш не положить и в маркер. Поэтому по возможности хэш записать и явно сказать, что делать, когда его нет (media-only и пустые сообщения — `_compute_raw_hash` возвращает `None`).

**Ещё одна деталь провенанса, которую легко проглядеть:** `_build_dedup_mirror` ставит `metadata['dedup_of'] = original.source_ref`, а `original` сам может быть зеркалом — то есть цепочки `dedup_of → dedup_of` возможны уже сегодня. Решить, разворачивать ли ссылку до истинного канонического документа, и записать решение; молча удлинять цепочку не стоит.

### 3.2.1 Что тянет за собой новая строка — проверить ДО выбора формы

Новая строка в `processed_documents` не инертна. `scheduler_service` вычисляет `new_doc_refs` как **разницу** снимков `list_source_refs_by_channel` до и после пайплайна, и эта разница уходит в три места:

- `run_incremental_topicization` — Phase 1 (дешёвое назначение) и Phase 2 (**LLM discover**);
- `watchlist_service.check_interests` — скоринг с эмбеддингами и **пуш алерта в чат пользователю**;
- `near_duplicate_service.run_near_duplicate_check_for_channel` — наблюдение.

Отсюда два вопроса, на которые сессия обязана ответить **фактом из кода, а не рассуждением**, потому что от них зависит форма фикса:

1. **Не переложим ли мы расход из processing в топикизацию?** Если дубликат становится `new_doc_ref`, Phase 2 может тратить на него LLM. Тогда экономия окажется бумажной.
2. **Не получит ли пользователь дубль алерта?** Дубликат — это новый `source_ref` с тем же текстом; watchlist сматчит его как отдельный документ. Это уже не про деньги, а про доверие к алертам — тот же класс, что BUG-095.

Важно: строки-зеркала pre-LLM живут с июля и **уже** проходят по этому пути, поэтому сегодняшнее поведение — это факт, который надо посмотреть, а не гипотеза. Если окажется, что зеркала действительно доезжают до Phase 2 и до watchlist, форма (C) становится предпочтительной, и это надо сказать прямо, даже если она дороже в реализации.

### 3.3 Что происходит со счётчиками R10 — решить, а не обнаружить

Если выбрана форма (A) или (B), отброшенный документ становится сохранённым, и это меняет арифметику, которую R10 только что выстроила. При форме (C) счётчики не меняются вовсе — и это одно из её преимуществ, которое стоит явно положить на чашу весов:

- `deduplicated_count` на стабильном канале должен уйти в **ноль** — именно это и есть наблюдаемый признак, что фикс работает (было ежетиковое плато, потому что те же документы возвращались каждый тик);
- **документ начнёт считаться `processed`, и это не догадка:** `processed_count = len(processed_docs)` ([`processing_service.py`](../../tg_parser/services/processing_service.py) ~335), а пайплайн возвращает `results` вместе с зеркалами (`results.extend(persisted_mirrors)`); комментарий там же (~411) прямо говорит про pre-LLM зеркала «These produce a persisted mirror row (counted in `processed_count`)». Значит выбор стоит так: либо принять, что запись дубликата — это «обработанный документ» (консистентно с S3), либо исключить её из `processed_count` и объяснить, чем эти две записи различаются. Молчаливо получить третий вариант нельзя — надо решить;
- тесты R10 должны остаться зелёными; если ломаются — это сигнал, что смысл счётчика изменился, и изменение надо описать в BUG-097, а не подогнать assert.

### 3.4 Раскладка остатка по трём механизмам

Теперь она нужна не для оценки экономии (её дал замер), а чтобы решить **стоит ли вообще** переносить проверку перед LLM. Разложить дубликаты по: (1) нормализация LLM, (2) legacy-строка без `raw_content_hash`, (3) media-only / пустое сообщение. Источник — прод: `dedup_db_duplicate` события против `metadata` канонических документов и наличия текста у сырых. Доля (3) не стоит токенов вовсе; доля (2) лечится бэкфиллом `raw_content_hash`, а не порядком; доля (1) переносом не лечится никогда.

### 3.5 Перенос проверки / бэкфилл — только если §3.4 показала долю, ради которой это оправдано

Это третий шаг, и он может закончиться записью «не оправдано». Экономия здесь — **один** вызов на документ, тогда как §3.2 экономит все последующие.

### 3.6 Вне scope

- **Классификация исходов** — сделана в R10.
- **`get_pipeline_status`** — новых полей не добавлять, решение R10 в силе.
- **Качество выдачи поиска на существующих зеркалах.** Строки-зеркала живут с июля, и вопрос «должен ли поиск отдавать два почти одинаковых документа» существует **независимо** от этой сессии. Проверить, как обстоит дело сегодня ([`retrieval_service.py`](../../tg_parser/services/retrieval_service.py)), и **записать диспозицию** — но не переделывать здесь ранжирование: иначе сессия про деньги превратится в сессию про качество поиска.
  ⚠️ Это **не** относится к §3.2.1: последствия для топикизации и watchlist — не диспозиция, а вход в выбор формы фикса. Их надо проверить и учесть, а не отложить.
- **Схема БД.** Миграция в этой сессии не нужна, и контракт проверен прямо при подготовке промпта: в [`processed_document.schema.json`](../contracts/processed_document.schema.json) `metadata` — `type: object` с `additionalProperties: true`, и `additionalProperties: true` стоит также на верхнем уровне. Добавление или переиспользование ключей `dedup_of` / `raw_content_hash` контракт не нарушает. Если правишь **другой** contract-файл — перепроверяй заново.

## 5. Замеры: чем мерить до и после

Все read-only, с `required_permissions: ["all"]`.

⚠️ **Разбивка по `success` больше не работает как замер (b).** До R10 дедуп маскировался под отказ, и `GROUP BY success` разделял «дедуп» и «настоящую работу» побочно. После деплоя R10 `success = true` практически всюду, а `failed_count` = 0 — тот запрос теперь даёт одну строку и не сравним с базой из §1. Мерить надо по новому счётчику:

Расход и дедуп по тикам (главное число сессии):

```bash
ssh prod "docker exec tg_parser_postgres psql -U tg_parser_user -d tg_parser -P pager=off -c \"SELECT date_trunc('hour', attempt_at::timestamptz) AS tick, sum(coalesce((details_json::jsonb->'pipeline_stats'->'process'->>'deduplicated_count')::int,0)) AS dedup, sum(coalesce((details_json::jsonb->'pipeline_stats'->'process'->>'processed_count')::int,0)) AS processed, sum(coalesce((details_json::jsonb->'pipeline_stats'->'process'->>'failed_count')::int,0)) AS failed, sum(coalesce((details_json::jsonb->'pipeline_stats'->'process'->>'total_tokens')::int,0)) AS tokens FROM source_attempts WHERE attempt_at::timestamptz > now() - interval '24 hours' GROUP BY 1 ORDER BY 1 DESC;\""
```

Признак работающего фикса — не одно нулевое значение, а **падение `dedup` от тика к тику**: 27 на первом тике после R11 (документы записываются впервые), затем ноль на стабильном канале. `coalesce` здесь обязателен из-за холостых тиков без ключа (см. состояние на входе).

Повторность — тот же документ на нескольких тиках (доказательство цикла):

```bash
ssh prod "docker logs tg_parser 2>&1 | grep dedup_db_duplicate > /tmp/dd.jsonl; wc -l < /tmp/dd.jsonl; python3 -c \"
import json,collections
refs=collections.Counter(); ts=[]
for l in open('/tmp/dd.jsonl'):
    d=json.loads(l); refs[d['source_ref']]+=1; ts.append(d.get('timestamp',''))
print('window', min(ts), '->', max(ts))
print('unique', len(refs), 'events', sum(refs.values()))
print('once-only', sum(1 for v in refs.values() if v==1))
print(refs.most_common(5))
\"; rm -f /tmp/dd.jsonl"
```

База 2026-08-13: 81 событие, 27 уникальных, `once-only` = **0**. После фикса ожидание обратное: каждый документ встречается **один** раз, `once-only` = число уникальных.

Метрика дедупа по каналам (существует давно, история есть):

```bash
ssh prod "docker exec tg_parser_prometheus wget -qO- 'http://localhost:9090/api/v1/query?query=tg_dedup_duplicates_detected_total'"
```

⚠️ Счётчик обнуляется при пересоздании контейнера, поэтому сравнивать абсолютные значения до и после деплоя нельзя — только `increase()` внутри одного времени жизни процесса. Хуже того: **сразу после пересоздания мгновенный запрос возвращает пустой vector**, потому что у counter'а с лейблами нет серии до первого инкремента — это выглядит как «метрика пропала». Базу до деплоя брать из истории через `&time=<unix>`, а не мгновенным запросом (проверено в R10-деплое, см. §3–§4 runbook'а).
