# START PROMPT — S2: авто-калибровка порога watchlist при создании интереса

**Дата создания:** 2026-06-08 (конец сессии S1→S3) · **Для:** новой сессии обсуждения → планирования → реализации S2.
**Goal (одной строкой):** при создании F11-watchlist предлагать (а не хардкодить 0.6) порог `threshold` на основе фактического распределения combined-скоров по корпусу, чтобы новый интерес не оказывался «мёртвым» из-за недостижимого порога.

> **Рабочий режим (нормативно, [`AGENTS.md`](../../../AGENTS.md)):** branch `main`; `git commit` и деплой — **только по явному запросу пользователя**; `docs/methodology/**` — вне этого workspace; `pyproject.toml`/`requirements.txt` — не трогать без явного запроса. Scope — **только watchlist threshold calibration**, не задевать unrelated-код. Принцип сессий S1/S3: **сначала обсуждаем дизайн → фиксируем развилки → потом реализуем**; dry-run/advisory по умолчанию, мутации — явное действие оператора.

Системный roadmap (выведен в сессии 2026-06-08 из разбора первопричины «watchlist не матчит»):

| Шаг | Что | Статус |
|---|---|---|

| **S3** | backfill rework: дефолт = весь корпус, uncapped batched scoring, тихий apply за подтверждением | ✅ задеплоено, ADR-0011 |

**Почему S2 именно сейчас (и был заблокирован до S3):** S2 должен предлагать порог из распределения combined-скоров по корпусу. До S3 backfill был зажат cap-ом 2000 newest-docs и дефолтным cutoff=`created_at` (пустое окно для нового интереса) → распределение было недостоверным. После S3 полнокорпусный скоринг доступен «из коробки» — это и есть фундамент S2.

## 2. Первопричина, которую закрывает S2

Из диагностики: исходный провал «watchlist не матчит» имел **две** независимые причины.
- **(1) Штраф знаменателя** в keyword-recall → закрыто **S1** (`topk`).
- **(2) Порог — голое магическое число без подсказки.** Дефолт `watchlist_default_threshold = 0.6` недостижим для многих интересов (особенно при весе semantic 0.6 и потолке cos ~0.7 на русмед-тексте). Оператор не знает, какой порог реалистичен. → **это и есть зона S2.**

S2 не меняет scoring-модель (S1) и не меняет backfill (S3) — он добавляет **рекомендацию порога** поверх них.

## 3. Текущая реализация — точки интеграции (сверено с кодом 2026-06-08)

### 3.1 Создание интереса — где сейчас ставится порог
[`tg_parser/services/watchlist_service.py`](../../../tg_parser/services/watchlist_service.py):

- `WatchlistService.create_interest(..., threshold: float | None = None, ...)` (~стр. 595-641) и `WatchlistService.subscribe(..., threshold: float | None = None, ...)` (~стр. 643+) — оба основных пути создания.
- Порог резолвится так:
  ```
  threshold=_resolve_default_threshold(threshold)   # None → settings.watchlist_default_threshold (0.6)
  ```
  `_resolve_default_threshold` — ~стр. 213.
- **Важно для S2:** оба пути **eager-эмбеддят интерес сразу при создании** (`_embed_interest`, create_interest ~стр. 636; subscribe аналогично). То есть на момент калибровки эмбеддинг интереса УЖЕ есть — можно сразу скорить корпус, без отдельного lazy-шага.
- Канонический текст эмбеддинга: `build_canonical_interest_text` (~стр. 528) = description → title → keywords.
- На UPDATE-пути `subscribe` (idempotent upsert, `_apply_upsert` ~стр. 769) эмбеддинг пересчитывается при изменении text-полей (description/title/keywords). Релевантно для под-кейса «рекалибровка порога при изменении интереса» — но для S2-MVP целимся в момент создания; рекалибровку на апдейте обсудить отдельно (Р3/Р5).

### 3.2 Скоринг и полнокорпусный проход (после S3)
- `compute_watch_score(interest, doc, doc_embedding, *, keyword_weight, semantic_weight, aggregation, topk)` (~стр. 306) — чистая функция; `combined = kw_w*keyword + sem_w*semantic`, `keyword` = topk-recall (ADR-0010).
- `WatchlistService.backfill_interest(interest_id, *, since=None, limit=None, dry_run=True)` (~стр. 1075+) — после S3: `since=None` ⇒ весь корпус; uncapped; batched эмбеддинги `embedding_repo.get_many_by_source_refs` (ADR-0011). Возвращает `BackfillResult(scored_docs, max_combined, would_match, ...)`.
- **NB:** `BackfillResult` сейчас отдаёт только агрегаты (`max_combined`, `would_match`), НЕ полное распределение combined-скоров. Для S2 распределение придётся либо вернуть из backfill (расширить результат), либо посчитать отдельным calibration-проходом, переиспользующим тот же scoring-код. Это одна из развилок (см. §5).

### 3.3 Точки вызова создания (CLI / MCP / bot)
- CLI: `tg_parser/cli/watchlist_cmd.py` (subscribe/create команды; backfill — ~стр. 369, уже с `--yes` после S3).
- MCP: `tg_parser/mcp_server.py` — `subscribe_watchlist` (создание), `backfill_watchlist` (~стр. 3263, после S3 с `confirm`).
- Bot: `tg_parser/bot/tools.py` — intent subscribe_watchlist. (Backfill-tool у бота НЕТ — выяснено в S3.)

### 3.4 Настройки
[`tg_parser/config/settings.py`](../../../tg_parser/config/settings.py) ~стр. 661-700:
- `watchlist_default_threshold = 0.6` (стр. 683) — текущий хардкод-дефолт, который S2 должен заменить/дополнить рекомендацией.
- `watchlist_keyword_weight=0.4`, `watchlist_semantic_weight=0.6`, `watchlist_keyword_aggregation="topk"`, `watchlist_keyword_topk=3`.

## 4. Что такое S2 — суть фичи

При создании интереса (когда эмбеддинг уже посчитан), прогнать лёгкий скоринг по корпусу его каналов и из распределения combined-скоров **предложить** реалистичный порог, вместо слепого 0.6.

Принципиальный водораздел (решить в §5): **advisory** (вернуть `suggested_threshold` + обоснование, оператор подтверждает/правит) vs **auto-set** (сразу записать рекомендованный порог). По духу сессий S1/S3 (dry-run-first, оператор в контроле) дефолт — скорее advisory, но это надо обсудить.

## 5. Открытые развилки дизайна (повестка обсуждения)

### Р1. Алгоритм выбора порога из распределения
Варианты (не взаимоисключающие):
- **(a) Перцентиль** распределения combined (напр. порог = 90-й перцентиль) — просто, но чувствительно к объёму/шуму канала.
- **(b) Целевой объём матчей** — подобрать порог под ~N матчей за период (или top-X% корпуса). Интуитивно для пользователя («хочу ~5 алертов в неделю»).
- **(c) Knee/gap-детекция** — найти разрыв между on-topic кластером и шумовым полом, поставить порог в зазор. Точнее, но сложнее и хрупко на малых выборках.
- **(d) Отступ от потолка** — `max_combined − margin`. Дёшево, но max чувствителен к одному выбросу.
- *Рекомендация к обсуждению:* стартовать с (b) или (a) как MVP; (c) — как улучшение.

### Р2. Источник распределения
- Расширить `BackfillResult`/`backfill_interest`, чтобы вернуть распределение (список/гистограмму combined), переиспользовав S3-проход; **или**
- отдельный `calibrate_threshold` метод сервиса, зовущий тот же scoring-код. Развязка ответственностей vs дублирование.

### Р3. Advisory vs auto-set (и где гейт)
- advisory по умолчанию + явное подтверждение для записи (паттерн S3 `--yes`/`confirm`), либо auto-set с возможностью override. Согласовать с принципом «оператор в контроле».

### Р4. Стоимость/латентность при создании
- Полнокорпусный скоринг синхронно при создании может быть медленным (тысячи доков × каналы; pymorphy + batched эмбеддинги). Варианты: синхронно (приемлемо?), фоновая задача с последующим уведомлением рекомендации, или sampling корпуса для оценки распределения.

### Р5. Edge-cases / фоллбэки
- Эмбеддинг-клиент недоступен (нет semantic) → калибровать по keyword-only или фоллбэк на дефолт?
- Канал без документов / только что добавленный → нет данных → фоллбэк на `watchlist_default_threshold`.
- Очень маленький корпус → доверительный интервал низкий → не навязывать, помечать как «низкая уверенность».
- Несколько каналов с разными шкалами → агрегировать распределение или по худшему/среднему?

### Р6. Конфигурируемость
- Новые `Settings`-флаги (стратегия калибровки, целевой перцентиль/объём, вкл/выкл) по образцу `watchlist_*` полей — или хардкод MVP с последующим выносом? (В S1/S3 выносили в Settings.)

## 6. Принятые ранее решения, релевантные S2 (не пересматривать без причины)

- **S1 / ADR-0010:** агрегация `topk` (K=3), `min(hits,k)/k`; веса 0.4/0.6 фиксированы; пороги при S1 НЕ трогали (no-op для ≤3 ключей). S2 калибрует поверх `topk`-шкалы — распределения уже «после S1».
- **S3 / ADR-0011:** backfill дефолт = весь корпус, uncapped, batched; apply тихий (`notified=True`) за подтверждением; go-forward scheduler без изменений. S2 переиспользует этот scoring-путь.
- **Мониторинг:** опциональный `+0.05` к порогу широких интересов (GLP-1, Биомаркеры) — операционный рычаг; S2 не должен ему противоречить (калибровка и ручной бамп — разные слои).
