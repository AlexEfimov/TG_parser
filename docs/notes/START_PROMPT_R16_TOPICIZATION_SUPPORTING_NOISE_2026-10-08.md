## 2. Scope

**Входит:**

1. **Симуляция на прод-данных — первый шаг и точка остановки.** Новый read-only скрипт `scripts/r16_supporting_simulation.py`, запуск на проде как в R6 (`docker cp` в `tg_parser`, `scripts/` в образ не входит). Скрипт **вызывает продуктовый скоринг** с параметрами, а не копирует его, как `s5`: иначе прогноз меряет копию. Если для этого нужны параметры у `_compute_match_score` / `_tokenize`, их добавление — часть сессии.

   Оси (полный перебор не нужен — сначала по одной от базы, затем лучшие сочетания):
   - стоп-лист: нет / затравка R6 / затравка + добавки аудита / + кандидаты из частот §1;
   - отсечка supporting: `<` / `<=`;
   - агрегация **для supporting**: `topk_denom` / `mean` (Phase 1 остаётся на `topk_denom`, если п. 2 не решит иначе). Для тем с `n_keywords ≤ 3` схемы совпадают, так что ось что-то меняет только на темах шире K;
   - порог supporting: 0.10 / 0.15 / 0.20;
   - фильтр по частоте внутри канала: ключевое слово темы не считается, если встречается в > X % документов канала (X = 15 / 25 / 40, как `DF_FRACTIONS` в R6).

   Выход по каждому каналу и конфигурации, **отдельно для тем с `n_keywords ≤ 3` и `> 3`**: тем на документ, медиана `items`, число тем с ≥ 100 supporting, **документы вне всех бандлов** (это нагрузка на сверку BUG-075 → Phase 2), для Phase 1 на последних N документах канала — назначено / не назначено против базы (прогноз числа вызовов discover × ~$0.85). Плюс глазами: по 3 темы в 4–5 каналах — что ушло из бандла и что осталось.

   **Стоп:** таблица → владелец выбирает конфигурацию (решение 1). Результат — `docs/notes/R16_SUPPORTING_SIMULATION_<дата>.md`.
2. **Правка кода по выбранной конфигурации.** Общий стоп-лист — один модуль, без второй копии. Отсечка, агрегация для supporting (если выбрана отдельная — своя настройка, а не смена `topicization_assign_keyword_aggregation`), фильтр по частоте (если выбран). **Детерминированный тай-брейк** перед срезом до 100: `(-score, source_ref)`. Докстринг `_tokenize`. **Phase 1** (решение 2): стоп-лист в `_tokenize` её заденет неизбежно — принять, если симуляция не показала роста «не назначено», иначе развести токенизацию путей. Порог Phase 1 (`>=`) без отдельного решения не трогать.
3. **`KEYWORD_STOPLIST` аналитики** (решение 3). Рекомендация — в R16 бит в бит: смена набора сдвигает Jaccard всех связей, а порог 0.32 откалиброван на текущем. Общий модуль может держать два именованных набора. Расширение для линковки — в R18, с прогоном `r6_stoplist_simulation.py`.
4. **Зеркалирование ручек в compose** — все `TOPICIZATION_*` из §1, которые читает воркер, плюс новые из п. 2, со ссылкой на BUG-092 и записью в `SCHEDULER_CRITICAL_ENV`. Без этого откат конфигурации — только новым образом. Перед этим снять с прода **имена** заданных `TOPICIZATION_*` в `.env` (без значений других ключей): после зеркалирования они начнут действовать на воркер.
5. **`max_tokens` стадии `topicization` вверх** (например, 16384) — после сверки лимита вывода модели стадии (`get_llm_config`). Батч не уменьшать: это удваивает входные токены (аудит, «Верификация» §4).
6. **Пересборка supporting без LLM — ответ на вопрос плана про O1.** Инструмент (CLI-команда или скрипт; по умолчанию dry-run): пересчитывает supporting существующих карточек канала новой конфигурацией. Инварианты:
   - якоря не меняются; id тем не меняются, поэтому связи (`topic_links` строятся по карточкам) не затрагиваются;
   - элементы `incremental llm assign` сохраняются — это оплаченные решения LLM, по ключевым словам они могут не пройти;
   - сохранение через `upsert`, **не** через `add_items` — иначе счётчик F5-C поднимется на весь бандл и запустит пересуммаризацию;
   - покрытие (решение 4): документ, который до пересборки был хотя бы в одном бандле, остаётся хотя бы в одном — в своей лучшей теме, как назначила бы Phase 1. Иначе сверка BUG-075 отправит выпавших в Phase 2;
   - выполняется под тем же advisory lock, что инкрементальная топикизация канала, либо строго между тиками.

   Применение на проде — отдельным шагом по GO (§5). **Вопрос плана про O1** (решение 5) промпт не закрывает. Владелец отвечает на него по таблице симуляции; сессия только записывает ответ в `PLAN_REMEDIATION` §4a:
   - если пересборка без LLM работает — расширять ли O1 с двух каналов на все каналы инстанса? Это вопрос плана дословно: у остальных каналов бандлы тоже на потолке, id тем при пересборке не меняются, связи не затрагиваются. Нужна ли сверх того LLM-перетопикизация карточек `aiinsideteam` и `physics_of_business` (~450k токенов) — отдельный вопрос, его тоже решает владелец: карточки строит LLM, и этот дефект их сам по себе не задевает;
   - если пересборка не работает — оставлять ли O1 плановой перетопикизацией двух каналов или расширять этот LLM-прогон на все каналы? Решает владелец.

**Не входит:**

- линковка полного прогона, область `link_topics`, CLI-дефолт порога (R18);
- потолок контекста Phase 2 (R17);
- перетопикизация (O1) — только данные для решения 5;
- расширение `KEYWORD_STOPLIST` аналитики, если решение 3 — «бит в бит»;
- `MAX_SUPPORTING_ITEMS` как ручка — потолок остаётся страховкой, а не способом отбора;
- модель владения каналом.

## 3. Ловушки

- **Стоп-лист сам по себе не поможет** (§1: 3.7 %). Не выдавать «стоп-лист + `<=`» за фикс, пока симуляция не показала эффект на тем-на-документ.
- **Phase 2 — главный риск по деньгам**, и в него ведут две двери: (1) Phase 1 назначает меньше → больше discover на каждом тике; (2) документ выпал из всех бандлов → сверка BUG-075 кормит им discover по 200 на канал за тик. Вызов discover — ~290k input-токенов Sonnet (BUG-108). Обе двери меряются симуляцией до кода и проверяются после деплоя (§5 п. 6).
- **Аналитика и линковка.** Общий модуль, импортированный в `analytics_service`, не должен молча сменить набор слов — это сдвиг всех ~5k связей мимо R18.
- **Ручки через `.env` на воркер не доходят** (§1). Нельзя «попробовать порог через env» на проде без п. 4. После п. 4 уже заданные в прод-`.env` значения начнут действовать — сверить заранее.
- **«До» — смесь формул** (§1). Сравнивать надо симуляцию «база = текущий код на текущих карточках» против кандидатов, а не кандидатов против сохранённых бандлов. Иначе часть эффекта припишется правке, а это эффект пересборки.
- **Пересборка теряет LLM-назначения** (2 510 элементов), если собирать бандл только из `_compute_topic_bundle`. И поднимает F5-C-счётчик, если писать через `add_items` (`RESUMMARIZE_TRIGGER_N = 5`, до 10 тем за тик — LLM-шторм).
- **Гонка с тиком.** Инкрементальная топикизация дописывает бандлы через `add_items`; пересборка через `upsert` поверх затрёт свежие элементы. Нужен lock канала или окно между тиками.
- **Тёзки в стоп-листе.** Трёхбуквенные медицинские аббревиатуры (`СОЭ`, `ТТГ`, `ПЦР`, `IgE`) — ради них `min_token_length = 3`. В стоп-лист попадают только служебные слова; кандидатов из частот проверять глазами.
- **Нагрузка симуляции на прод.** `mediamedics` — 260 тем × 11 605 документов, substring-fallback квадратичен по токенам. Сначала замерить один средний канал; запускать между тиками; сессия к базе — read-only (`SET default_transaction_read_only = on`).
- **Ad-hoc SQL к проду** из агентской сессии может блокироваться автопроверкой — тогда повтор через карточку подтверждения владельца, а не обход.
- **Ждать конец тика по фиксированной строке:** `grep -F 'Incremental pipeline completed'` — шаблон с `Job "…` в JSON-логе не совпадает (R14).
- **Бэкап — вне рабочей копии** (`/mnt/data/backups/tg_parser/…`, каталог `700`).
- **Два параллельных полных прогона** на одной `tg_parser_test` конфликтуют (`DROP SCHEMA`) — PR standard по очереди.
