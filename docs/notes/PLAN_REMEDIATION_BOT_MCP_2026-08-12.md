# PLAN — Remediation-сессии по итогам код-ревью bot + MCP

**Тип документа:** planning plan (session-sequence) — planning artifact only, **ноль кода**.
**Дата:** 2026-08-12 · **Основание:** [`CODE_REVIEW_BOT_MCP_2026-08-12.md`](CODE_REVIEW_BOT_MCP_2026-08-12.md) — 12 находок (2 High, 5 Medium, 5 Low), §7 «Предложение remediation-сессий».
**Статус:** `proposed` — план последовательности работ; ни одно изменение кода не производится и не предлагается к немедленному применению.
**Branch:** `main`. Тестовые режимы — по [`tests/README.md`](../../tests/README.md); **PR standard (`TEST_POSTGRES=1`) обязателен для всех шести сессий**, потому что каждая трогает app-code (bot / MCP / API / repos).

## 0. TL;DR

- **Шесть сессий R1–R6**, идентификаторы наследуют §7 артефакта. Единственное уточнение против §7: **R4 разделена на R4a и R4b** — дешёвая правка пути файла нужна при любом выборе архитектурного лечения и не должна ждать решения.
- **Порядок:** `BUG-095 → R1 → R2 → BUG-094 → R4a → R4b → R3 → R5`; параллельным треком — `BUG-097`, `BUG-098(b)`, `R6`.
- **Главный принцип упорядочивания — не severity, а «кому сегодня больно».** Оба High из ревью **латентны**: они не стреляют ровно потому, что на проде не выпущено ни одного не-admin-токена. BUG-095 (алерты watchlist не доходят с 2026-06-15) ломает фичу у живого единственного пользователя прямо сейчас. Очередь, построенная по severity в вакууме, поставила бы латентное впереди актуального.
- **Для латентных находок правильная форма — гейт, а не приоритет:** R1 и R2 обязаны быть закрыты **до выпуска первого не-admin credential**, а не «срочно». Пока арендатор один, их можно планировать спокойно; в момент появления второго пользователя они становятся блокирующими.
- **Новая улика, полученная при подготовке плана** (§1): static-token путь на проде сконфигурирован, обязателен и при этом не используется. Это удешевляет R1 и добавляет ему второй бесплатный deliverable.

## 1. Улика, полученная при подготовке плана (read-only, прод)

Артефакт ревью помечает у F-01 `Runtime check needed: да`. Часть этой проверки выполнена при подготовке плана — только чтение, без изменений:

```
MCP_AUTH_ENABLED=true
MCP_AUTH_TOKENS: present, len=66
container tg_parser_mcp started: 2026-08-12T13:11:15Z
static_fallback_used : 0
mcp.request.received : 5384      # INFO-логирование живое
mcp.tool.start       : 10
```

Три следствия для R1:

1. **Static-token путь холодный.** Все аутентифицированные вызовы резолвятся через БД; событий `mcp.auth.static_fallback_used` — ноль. Значит фикс, который перестаёт молча выдавать admin, не рискует закрыть живой рабочий доступ. **Оговорка:** окно — одна жизнь контейнера и ~10 tool-вызовов, так что вывод надёжен по форме, но не по объёму; R1 всё равно открывается замером на длинном окне.
2. **Мёртвая конфигурация при этом обязательна.** `create_mcp_server` (`mcp_server.py:393–406`) при `MCP_AUTH_ENABLED=true` и пустом `MCP_AUTH_TOKENS` падает с `RuntimeError` — это guard BUG-001b. То есть защита, поставленная против молчаливого admin-fallback, сегодня **обязывает** прод носить живой bearer-токен с правами полного администратора, которым никто не пользуется, и именно он делит код-путь с деградацией F-01. Текст самого `RuntimeError` это наполовину признаёт: «Either provide static tokens or rely solely on DB-resolved tokens».
3. **Тот же паттерн живёт на третьей поверхности и пришпилен тестом.** `api/auth.py:58–63`: валидный статический `api_key` без DB-маппинга → `get_default_admin()`; ожидание закреплено в `tests/test_f4_auth_resolution.py::test_valid_key_not_mapped_falls_back_to_admin`. Это не расширяет scope ревью (HTTP-поверхность в него не входила), но R1 обязан сказать вслух, чинит он MCP или паттерн — иначе близнец останется незамеченным.

## 2. Сессии

### R1 — резолв идентичности перестаёт деградировать в admin (F-01)

- **Scope:**
  - **Замер первым шагом:** `mcp.auth.static_fallback_used` на максимальном доступном окне. Логи ротируются (`max-size=10m`, `max-file=3`), поэтому при необходимости — временный счётчик Prometheus и сутки ожидания. Вопрос: пользуется ли кто-нибудь статическим токеном.
  - **Разделить два случая, слитых сегодня в один `return await get_default_admin()`** (`mcp_server.py:500–547`): `client_id`, который является UUID и не резолвится (`db_user is None`) либо роняет запрос, — это **отказ** (`PermissionError`, как уже делает ветка `client_id is None`); `client_id`, который заведомо не UUID, — легальный legacy static-путь, оставить.
  - Сузить `except Exception` до транспортных/`SQLAlchemyError`; поднять `logger.debug("resolve_mcp_user: DB lookup failed…")` до `warning` — сегодня событие деградации не видно на INFO.
  - **Снять обязательность мёртвого токена:** разрешить `MCP_AUTH_ENABLED=true` при пустом `MCP_AUTH_TOKENS` (DB-only режим), сохранив исходный смысл BUG-001b — «не падать в admin молча».
  - **Решение по близнецу:** явно записать в сессии, чинится ли `api/auth.py:58–63` тем же PR или остаётся с зафиксированной диспозицией. Рекомендация — записать диспозицию, а код не трогать: HTTP-поверхность в ревью не входила и своей улики по ней нет.
  - **Out of scope:** bot-арм (`current_user or await get_default_admin()` в 34 исполнителях) — 34 точки правки и смена контракта сигнатуры; защита сегодня реально обеспечивается `UserResolutionMiddleware`. Место этой правки — hardening после R2, когда тестовая дисциплина «вызов без личности» уже выстроена.
- **Rationale / порядок:** пока резолв личности fail-open, вердикт **любой** другой проверки прав условен — поэтому первым в MCP-треке. Не раньше BUG-095 только потому, что BUG-095 болит у живого пользователя, а это — нет.
- **Deliverable:** сбой БД и удалённый пользователь дают отказ, а не полного администратора; деградация видна в логах на INFO; прод перестаёт носить неиспользуемый admin-credential.
- **Test strategy:** режимы default + PR standard. Существующие: `tests/test_mcp_auth_integration.py` (шесть кейсов, включая `test_production_mode_no_identity_fail_loud` и `test_meta_client_id_attack_is_ignored`), `tests/test_f4_auth_resolution.py`. Новые: три ветки резолва — UUID резолвится, UUID не резолвится → отказ, не-UUID → legacy admin; ветка «исключение при `get_owned_channel_ids`» (сегодня она тоже даёт admin). Прод-smoke после деплоя: рабочий токен продолжает работать, выдуманный UUID получает отказ.
- **Размер/риски:** **S**, риск средний — трогается auth. Гасится замером §1 и тем, что legacy-ветка сохраняется, а не удаляется.

### R2 — RBAC-паритет read-инструментов (F-02, F-10, второй путь F-04)

- **Scope:**
  - **F-02:** перенести в bot условие, которое уже есть в MCP (`mcp_server.py:1334–1347`): при заданном `channel_id` и непустом `allowed_channel_ids` — пустой результат вместо `list_by_channel`. Файл: `bot/tools.py:2102–2111`.
  - **F-10:** сверять владельца джобы в `get_export_status` (`mcp_server.py:3060`, сейчас `_user` резолвится и не используется) и в HTTP-скачивании (`api/routes/export.py:311`). Источник истины — `Job.client` либо новое поле `owner_user_id`; admin проходит сквозь, как везде.
  - **Второй путь F-04:** в `retrieval_service.py:293–308` `results.append(...)` стоит **вне** `if card:`, поэтому topic-хит с незагруженной карточкой возвращается в обход `allowed_channel_ids`. Занести append под проверку либо явно пропускать такой хит.
  - **Тест-обязательство — главный deliverable сессии:** параметризованный кейс «чужой идентификатор задан явно» для каждого read-инструмента, принимающего чужой id (`channel_id`, `topic_id`, `source_ref`, `job_id`, `interest_id`), на обеих поверхностях.
  - **Out of scope:** bot-арм F-01 (см. R1); любые изменения формы ответа (R3).
- **Rationale / порядок:** сам фикс F-02 — четыре строки, но это уже **третий подряд** дефект одного класса (BUG-093 — права на update-ветке, BUG-094 — поля, которые write не должен трогать, F-02 — фильтр на ветке с явным `channel_id`), и все три невидимы тестам по одной причине: тест описывает то, что код делает, а не то, чего он делать не должен. Ценность сессии — в закрытии класса, а не экземпляра. После R1, потому что до него любая проверка прав стоит на fail-open резолве.
- **Deliverable:** ни один read-инструмент обеих поверхностей не отдаёт чужие данные при явно заданном чужом идентификаторе; регресс этого класса ловится CI.
- **Test strategy:** режимы default + PR standard. Существующие: `tests/test_f4_ownership.py`, `tests/test_f4_coverage_supplement.py` (там же живёт `test_exec_list_topics_uses_list_by_channels_for_user`, который надо дополнить, а не заменить), `tests/test_f4b_scoping_read_tools.py`, `tests/test_bug093_add_channel_foreign_source.py` (образец red/green), `tests/test_f2_parse_only_export.py`. Новые: параметризованный набор выше; red/green на F-02 (с откатом фикса падает). Прод-smoke — как в BUG-093: одноразовый `user`-токен, проверка и отзыв.
- **Размер/риски:** **S**, риск низкий: все три правки сужают доступ, ни одна не расширяет. Побочный риск — ложные отказы у admin: закрывается тем, что `allowed_channel_ids is None` у admin проверяется первым.

### R4a — `file_path` с `job_id` (половина F-03)

- **Scope:** ключевать путь экспорта по `job_id` (`output/{job_id}/…`) у **всех трёх** писателей: `api/routes/export.py` (`_resolve_export_file`), MCP (через ту же функцию) и bot (`bot/tools.py:3724–3744`, собирает путь сам). **Out of scope:** всё, что относится к 404.
- **Rationale / порядок:** правка нужна при **любом** из трёх лечений BUG-096, ничего не ломает и ни от чего не зависит — держать её в очереди за архитектурным решением незачем. Сегодня две параллельные выгрузки одного уровня перетирают файл друг друга внутри контейнера, и это верно и для bot, который джобу вообще не создаёт.
- **Deliverable:** параллельные экспорты не сталкиваются; `file_path` в `api_jobs` однозначно указывает на артефакт своей джобы.
- **Test strategy:** default + PR standard. Существующие: `tests/test_export.py`, `tests/test_f2_parse_only_export.py`. Новые: два последовательных экспорта одного канала и уровня → два разных файла, оба читаются.
- **Размер/риски:** **XS**, риск нулевой. Единственная тонкость — старые джобы в БД с относительным путём: скачивание по ним должно продолжать работать (проверить обратную совместимость `download_export`).

### R4b — экспорт MCP по контракту ADR-0007 (F-03)

- **Scope:** `export_channel` в MCP перестаёт импортировать приватную `_run_export_job` из `tg_parser.api.routes.export` и исполнять её в своём процессе; вместо этого — POST на API, как уже делают `trigger_*` через `pipeline_dispatch_client`. Сюда же `get_export_status` (сейчас тянет `_resolve_job_level` оттуда же). **Out of scope:** bot-путь (он законно синхронный и шлёт файл в чат, ему хватает R4a); объектное хранилище.
- **Rationale / порядок:** это вариант **(b)** из BUG-096, и я предлагаю выбрать именно его, а не (a) «общий том». Аргумент: (a) лечит симптом и оставляет нарушение границы `api` → `mcp` — импорт приватного символа через границу адаптеров, — а с ним и следующий такой же дефект при следующей фиче. (b) приводит код к уже принятому ADR-0007 («MCP/Bot as thin HTTP clients») и к тому паттерну, который в этом же файле работает у `trigger_*`. После R4a — чтобы не переписывать путь дважды.
- **Deliverable:** `download_url`, выданный MCP-джобой, скачивается; из `mcp_server.py` уходит последний импорт приватного символа `api`.
- **Test strategy:** default + PR standard; **перед merge — max local** (`TEST_TESTCONTAINERS=1`), потому что дефект межконтейнерный. Существующие: `tests/test_export.py`, `tests/test_f2_parse_only_export.py`, CI-job `Compose Integration (MCP dispatch)` — сегодня он **skipped на docs-only PR** и не покрывает download-плечо; расширить его на скачивание, иначе класс невидим ровно так, как был. Прод-проверка: экспорт через MCP → GET по `download_url` → 200, и `raw_payload` в файле по-прежнему отсутствует.
- **Размер/риски:** **M**, риск средний — меняется способ исполнения фичи и, возможно, compose. Митигация: bot и HTTP-пути не трогаются, откат — возврат одного импорта.

### R3 — форма ответов read-поверхности (F-04, F-05, F-07)

- **Scope:**
  - **F-07:** обернуть `list_channels` в модель с сайдкаром (`degraded`) по образцу `SearchResults.degraded` (BUG-084), который уже живёт в `mcp_server.py`. Одна правка закрывает **и** маркер деградации (in-scope половина BUG-098), **и** исключение инструмента из пагинационного контракта TD-D-02 — оба следствия одного решения о типе возврата.
  - **F-04:** ветка для `entry_type="topic"` в `SearchResultItem` (title/summary из `topic_card`, `channel_id` из `card.sources[0]`) и сам `entry_type` наружу.
  - **F-05:** прекратить отдавать страницу под двумя ключами; назначить дату снятия `subscriptions` / `interests`; попутно необязательный фильтр `is_active` для `list_watchlists`.
  - **Парная правка `MCP_AGENT_GUIDE`** и **отложенные пункты [`AUDIT_DOCUMENTATION_2026-08-12.md`](AUDIT_DOCUMENTATION_2026-08-12.md) §6** (три секции F5-C, счётчики инструментов в `README`, оговорка к `download_url` — последняя снимается после R4b): один docs-заход вместо трёх.
  - **Out of scope:** производительность `coverage_counts_by_channel` — половина (b) BUG-098, отдельная сессия.
- **Rationale / порядок:** три находки — три проявления одного пробела: у tool-ответов нет описанного контракта (в `docs/contracts/` лежат только доменные артефакты). Это **breaking**-изменение формы, поэтому оно должно быть одним шагом с одной записью в справочнике, а не тремя. После R2 — потому что R3 переписывает те же проекции, в которых R2 расставляет проверки.
- **Deliverable:** деградировавшее покрытие отличимо от измеренного; topic-хит читаем; payload перестаёт удваиваться; `MCP_AGENT_GUIDE` описывает новую форму.
- **Test strategy:** default + PR standard. Существующие: `tests/test_mcp_pagination_contract.py`, `tests/test_pagination_contract_tdd.py` (**62 passed** на `f005f93` — базовая линия снята при ревью), `tests/test_channel_service_stats.py` (в т.ч. `test_batch_stats_degrades_to_zeros_on_aggregation_error`), `tests/test_f5a_hybrid_search.py`, `tests/test_mcp_server.py`. Новые: деградировавший ответ `list_channels` отличим от здорового; topic-хит несёт title/summary/channel_id; `list_channels` входит в пагинационный контракт.
- **Размер/риски:** **M**, риск — **breaking для потребителей**. Снятие legacy-ключей F-05 — решение владельца, а не правка: без окна депрекации оно ломает существующих клиентов ради размера ответа.

### R5 — четыре мелочи одним PR (F-06, F-08, F-09, F-11)

- **Scope:** `_MCP_INSTRUCTIONS:314` под фактическое поведение (F-06, одна строка); `topics.items` вместо `topics` в `resource_channel_topics` (F-09); `html.escape` на заголовке watchlist в `bot/tools.py:4722` (F-11); зажать `offset`/`limit` в одном месте (`utils/pagination.py` + `_paginate_read_result`) и добавить `minimum`/`maximum` в 10 INTEGER-параметров деклараций (F-08). Плюс три smoke-теста на MCP-ресурсы. **Out of scope:** вынос потолка страницы в настройку.
- **Rationale / порядок:** ни от чего не зависит, ничего не ломает, каждая правка ≤ 10 строк. Можно вытащить вперёд в любой момент, если нужен быстрый видимый результат; я не ставлю его первым только потому, что он не покупает ни безопасности, ни доверия к цифрам.
- **Deliverable:** описание сервера перестаёт обещать несуществующее поведение; третий MCP-ресурс оживает и покрыт тестом; «ещё» не зацикливается на отрицательном `limit`; заголовок с `<`/`&` не ломает отправку.
- **Test strategy:** default обязателен, PR standard перед merge. Новые: по одному тесту на находку + три smoke на ресурсы (иначе класс F-09 вернётся при следующей смене типа возврата).
- **Размер/риски:** **S**, риск нулевой. ⚠️ Если потолок страницы всё же выносить в настройку — новый ключ обязан попасть в compose allow-list, иначе значение в `.env` будет инертным (BUG-092). Проще обойтись константой.

### R6 — стоп-лист для keywords (F-12)

- **Scope:** стоп-лист (ru/en) или порог по df в `analytics_service._extract_keywords:48–59`, где единственный сегодняшний фильтр — длина токена ≥ 3; read-only симуляция «сколько связей уходит ниже `cross_channel_link_threshold=0.3`»; решение по порогу — по данным, в процессе ADR-0010. **Out of scope:** смена самой метрики cosine+Jaccard.
- **Rationale / порядок:** единственная находка вне двух ревьюируемых файлов и единственная, где фикс **без пересчёта делает хуже**: старые связи останутся с завышенными score, новые пойдут по новой шкале. Независима от всего остального, поэтому идёт параллельным треком.
- **Deliverable:** `shared_keywords` перестают показывать служебные слова; и, что важнее, `similarity_score` перестаёт их учитывать — сегодня те же токены формируют множества, по которым считается Jaccard; отчёт симуляции — артефакт сессии.
- **Test strategy:** default + PR standard. Существующие: `tests/test_topic_linking_service.py`, `tests/test_cross_channel_topicization.py`. Новые: unit на стоп-лист; snapshot-diff состава линков до/после.
- **Размер/риски:** **S/M**, риск средний — сдвигается состав TopicLink. Гасится симуляцией до включения.

| **BUG-094** — `add_channel` сбрасывает курсор ingestion | сразу за R2 | тот же класс тестового пробела, что F-02 и BUG-093; та же пара файлов; тестовая дисциплина R2 («проверять и то, чего write не должен трогать») переиспользуется как есть |
| **BUG-097** — дедуп после LLM | параллельный трек | pipeline, ничего из очереди не трогает; половина «классификация» дешёвая и снимает ложный `degraded` на 8 источниках |
| **BUG-098** — покрытие `list_channels` | половина (a) → **в R3**; половина (b) — отдельно | форма ответа и производительность запроса не связаны и не должны ехать вместе |
| **BUG-008** — MCP hang | не трогаем | `open` by design, ждёт живого повторения; чек-лист уже есть |

**Выдача `BUG-NNN`.** Номера в этом плане намеренно не зарезервированы: id выводится в момент записи командой из [`AUDIT_DOCUMENTATION_2026-08-12.md`](AUDIT_DOCUMENTATION_2026-08-12.md) §4. Маппинг «находка → предлагаемая запись» — в §7 артефакта ревью.

## 4. Граф зависимостей и очередь

```
BUG-095 ──► R1 ──► R2 ──► BUG-094 ──► R4a ──► R4b ──► R3 ──► R5
                                                  ‖
параллельный трек (другие subsystem'ы):  BUG-097 · BUG-098(b) · R6
```

Жёстких зависимостей ровно три:

- **R4a → R4b** — иначе путь файла переписывается дважды;
- **R2 → R3** — R3 меняет те же проекции, в которых R2 расставляет проверки;
- **R1 → всё остальное на MCP-поверхности** — пока резолв личности fail-open, вердикт любой другой проверки прав условен.

Всё прочее — предпочтения, а не блокировки. **R5 можно вытащить вперёд** в любой момент. **R6 не зависит ни от чего.** При исполнении вдвоём параллелятся R6 и любой из BUG-097 / BUG-098(b) с основной цепочкой.

## 5. Приоритизация — обоснование сквозного порядка

1. **Актуальное перед латентным.** BUG-095 — единственная запись, которая ломает ценность у живого пользователя: матчи пишутся, алерты не приходят два месяца. Оба High из ревью не стреляют, пока на проде один admin.
2. **Гейт вместо срочности для латентного.** R1 и R2 привязаны к событию («выпуск первого не-admin credential»), а не к дате. Это делает очередь устойчивой к изменению планов по многопользовательскому режиму — и одновременно даёт сессии #4 однозначный ответ на вопрос «что чинить прежде, чем продавать доступ второму арендатору».
3. **Сначала измерить, потом чинить — там, где фикс меняет живой путь.** R1 без замера — шанс закрыть доступ, которым пользуются. Замер наполовину сделан (§1) и результат удешевил сессию.
4. **Дешёвое и обязательное — вперёд архитектурного.** R4a нужна при любом лечении BUG-096 и стоит XS; держать её за решением по контейнерам незачем.
5. **Breaking-изменения формы — одним шагом.** F-04, F-05, F-07 правят одни и те же модели ответов; поодиночке они означали бы три правки `MCP_AGENT_GUIDE` и три окна несовместимости вместо одного.
6. **Один subsystem — одна сессия** (принцип из [`PLAN_REMEDIATION_SESSIONS_PROCESSING_ALGORITHMS_2026-07-07.md`](PLAN_REMEDIATION_SESSIONS_PROCESSING_ALGORITHMS_2026-07-07.md) §3.7): auth (R1), RBAC read-путей (R2), экспорт (R4a/R4b), модели ответов (R3), мелочи (R5), keywords (R6).
7. **Класс важнее экземпляра.** Главный deliverable R2 — не четыре строки фикса, а параметризованный тест «чужой идентификатор задан явно»: три подряд дефекта (BUG-093, BUG-094, F-02) прошли мимо CI по одной и той же причине.

## 6. Чего делать не стоит

- **Не поднимать `statement_timeout` под BUG-098** — это обмен неверного числа на медленную поверхность. Половина (a) из R3 честнее и дешевле.
- **Не лечить 404 экспорта общим томом** без решения по границе: симптом уйдёт, нарушение ADR-0004 останется, и следующая фича воспроизведёт его.
- **Не снимать legacy-ключи `subscriptions` / `interests` без окна депрекации** — это ломает потребителей ради размера payload.
- **Не убирать `or await get_default_admin()` из 34 bot-исполнителей в одном PR с R1** — другой риск, другой способ проверки, другая поверхность.
- **Не включать R6 без пересчёта линковки** — иначе старые связи останутся с завышенными score, а новые пойдут по новой шкале.
