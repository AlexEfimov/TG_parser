## 7. Lessons learned

1. **MCP probes surface second-site bugs that unit/integration
   tests cannot.** BUG-014B was discovered exclusively through
   AMBER live-probe in the post-deploy watch window — neither the
   2050-test pre-merge suite nor any pre-merge static analysis
   would have flagged it because the orchestrator callsite
   (`orchestrator.py:110`) is reached only when `rate_limit_until`
   is naive *and* not null *and* in the future, which is a runtime
   data condition, not a test fixture default. **Action for future
   sprints:** schedule a 30-min MCP-probe phase as part of the
   acceptance-signal verification, before declaring closure.

2. **Watch-window verdict GREEN ≠ all related bugs closed.** This
   sprint closes 3 bugs and **opens** 1 (BUG-014B). Mismatch is
   expected when the verification methodology improves (live MCP
   probes added in this cycle, were not present in F4-B Core
   watch window). Frame the marker as «closed scope X with
   discovered scope Y queued» rather than «all-clear».

3. **BUG-013 catch behaviour is observable in error counts.** With
   the per-task `try/except` in `_process_source`, every BUG-014B
   firing on the 2 affected sources still emits a JSON traceback
   carrying *both* `scheduler_service.py:201` and
   `orchestrator.py:110`. Naive `grep -c TypeError` therefore
   double-counts the same error event across two file mentions.
   **Action:** standardize evidence queries on
   `grep -E "TypeError.*offset" | grep -oE "/app/[a-z_/]+\.py:\d+"
   | sort -u` for the *originating* callsite instead of bare
   `-c`. Add to the `MCP_DEPLOY_VERDICT_PLAYBOOK.md` (will be
   created or updated when the runbook hygiene sprint runs).

4. **Per-tick `succeeded=N, failed=M` line is the cleanest closure
   evidence.** Across all 28 ticks, the shape was identical
   (`succeeded=7, failed=2, duration≈91s`). This single-line
   summary log encodes (a) BUG-013 closure (no whole-gather
   crash), (b) BUG-014B steady-state (constant failed=2), (c)
   scheduler health (consistent ~91s tick duration, ~3% of the
   1h cron interval). **Action:** make `Incremental pipeline
   completed: succeeded=N, failed=M, duration=Xs` a permanent
   first-class closure-evidence query (already grep-trivial; just
   needs to be promoted into the runbook).

5. **BUG-016 was masked by the same env-drift it caused.**
   Pre-PR #81, MCP-triggered pipelines failed at `Missing
   TELEGRAM_API_ID/HASH` long before they could exercise the
   scheduler. This hid BUG-015 (Telethon re-auth `EOFError`)
   until the env layer was fixed. **Action:** when fixing infra
   bugs, expect a layer-2 architectural bug to become newly
   visible — schedule a follow-up ADR slot in the same sprint
   pre-flight (we caught BUG-015 in PR #81's smoke probe, which
   is the right pattern).
